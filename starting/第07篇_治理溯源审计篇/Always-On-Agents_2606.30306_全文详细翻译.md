# Always-On Agents：LLM Agent 的持久记忆、状态与治理综述

> 原文：*Always-On Agents: A Survey of Persistent Memory, State, and Governance in LLM Agents*
> arXiv：2606.30306v1，2026-06-29
> 作者：Tianyu Ding、Aditya Nannapaneni、Bingfan Liu、Ling Zhang

## 摘要

“Always-on agent”指未来行为依赖于早先交互积累的持久状态的系统。本文把研究对象从狭义的可检索记忆扩大为完整的持久状态：除了记忆，还包括任务账本、权限、凭证、承诺、来源与审计记录、共享状态、触发条件，以及由这些记录连接起来的外部副作用。

作者用六条诊断轴分析每一种状态：**权威性（authority）、作用域（scope）、可变性（mutability）、来源（provenance）、可恢复性（recoverability）和可行动性（actionability）**；再用一条生命周期分析状态如何被写入、验证、组织、召回、使用、更新、遗忘、审计，必要时回滚。

作者对 435 篇工作做了编码，但强调这只是一个有范围的地图，不是穷尽式统计。总体趋势是：研究更集中于积累和召回状态，而对治理、恢复和主动放弃状态关注不足。为此，论文提出 Always-On Evaluation Protocol（AOEP-v0），把状态变更和恢复义务纳入评测，而不只看答案质量。

## 1. 什么是 always-on agent

论文的操作性定义是：如果一次交互产生的状态，会在后续交互中影响系统的观察、决策或行动，那么系统就属于持久状态系统。状态不局限于向量库中的文本条目，也包括任务是否完成、某项权限是否仍有效、某个承诺是否已经对外发出，以及某次工具调用是否改变了外部世界。

这一定义把五类相邻系统区分开：普通无状态聊天、一次性长上下文任务、只保存日志的应用、只有参数更新的持续学习系统，以及真正会在未来行动中使用并改变持久状态的 agent。判断标准不是系统有没有“记忆模块”，而是早先状态是否会继续约束后来行为。

## 2. 六条状态轴

### 2.1 权威性

authority 描述谁有资格创建、修改、撤销或覆盖一条状态。用户声明、工具返回、agent 自己的总结和另一个 agent 的转述不能默认拥有同等权威。权威还需要处理冲突：谁能否决谁，是否允许临时授权，授权是否会过期。

### 2.2 作用域

scope 说明状态对谁、哪个任务、哪个 agent、哪个时间段有效。私人偏好、团队事实、公共知识、某个项目的临时假设不应进入同一个无标签空间。作用域缺失后，最常见的问题不是找不到，而是把本不该看到的内容找出来。

### 2.3 可变性

mutability 区分原地覆盖、追加版本、只读事实和可撤销的临时状态。原地覆盖很方便，但会消灭历史和责任链；追加版本会增加存储和读取复杂度，却允许系统回答“当前值是什么”和“以前为什么是另一个值”。

### 2.4 来源

provenance 记录状态来自哪一次输入、哪个工具、哪个 agent、哪个用户和哪一版转换。来源不是装饰性元数据，它决定后续能否核验、撤销和归责。

### 2.5 可恢复性

recoverability 关注状态能否从错误、删除和污染中恢复。只有备份不一定够：恢复还要知道恢复到哪个一致性点，哪些派生状态也必须一起重建，哪些外部副作用已经无法撤回。

### 2.6 可行动性

actionability 描述状态是否能直接触发工具调用、发送消息、修改文件或其他外部副作用。可行动状态的治理门槛高于只用于回答问题的文本，因为错误会离开模型上下文进入现实世界。

## 3. 持久状态的分类

作者把传统 memory 分成 episodic trace、semantic fact、preference 和 procedural skill，又补充了治理真正需要的控制状态：工作流与任务账本、策略与权限、来源与审计、共享与社会记忆、触发状态、工具与凭证状态、外部承诺和副作用。

这些状态相互耦合。例如，一个“用户偏好”可能改变检索；检索出的偏好又可能改变工具参数；工具结果产生新的任务状态；任务状态最后触发外部承诺。若系统只对文本记忆做版本管理，整条链仍然可能不可审计。

## 4. 持久状态生命周期

论文把生命周期分成向前弧和返回弧。

向前弧是：

1. **observe**：观察输入、环境和工具结果；
2. **write**：决定哪些内容成为持久状态；
3. **validate**：检查来源、权限、格式和一致性；
4. **organize**：去重、合并、建立关系和索引；
5. **retrieve**：按当前任务和作用域取回状态；
6. **act**：用状态决定输出或工具行动。

返回弧是：

7. **update**：追加新版本或传播变化；
8. **forget**：降低可见性、删除或执行被遗忘请求；
9. **audit**：记录状态被谁、何时、以什么方式使用；
10. **rollback**：恢复到先前状态，并处理由错误状态产生的派生影响。

论文认为，现有工作最常研究 observe/write/retrieve，却经常把 validate、audit 和 rollback 当成系统外部工作。这样做的后果是：系统能够产生一个看似正确的答案，却说不清它为什么读到这条状态，也无法在状态污染后稳定恢复。

## 5. 状态载体与机制

论文比较了参数化状态、上下文窗口、RAG/vector store、知识图与时间记忆、多模态存储、agentic OS/runtime，以及资源和成本治理。没有一种载体天然提供完整治理能力。

- 参数化状态延迟低，但难以逐条撤销、解释和审计。
- 上下文窗口保留原始证据，却受预算限制，且不等于持久状态。
- 向量库便于召回，但相关性排序不能替代授权、版本和来源判断。
- 图和时间结构更适合表达关系与历史，但合并、冲突和一致性成本更高。
- runtime 可以把权限、触发器和外部副作用纳入控制面，却必须明确谁能改变控制面本身。

作者还强调“baseline beats memory”现象：记忆机制如果把错误、陈旧或不相关内容带进上下文，可能比没有记忆更差。因此评测必须把记忆造成的净收益和净伤害都测出来。

## 6. 失败模式与治理面

论文整理了几类持久性特有的失败：写入投毒和间接注入、召回干扰和工具漂移、陈旧承诺与信念漂移、删除失败和回滚缺口、跨 agent 传播、以及把回滚本身变成新攻击面的风险。

治理章节分别讨论 authority、permission、provenance、audit、privacy、consent、scope、生产环境中的公共记忆控制、删除传播和“被遗忘权”。核心观点是：治理不是在输出端加一个过滤器，而是贯穿状态从产生到行动的每一步。

## 7. AOEP：把治理义务纳入评测

AOEP-v0 的思路是给 agent 一个事件流和状态快照，观察它是否遵守状态变更和恢复义务。评测对象不只是“答案对不对”，还包括：

- 未授权状态是否进入上下文；
- 写入是否带有可验证来源；
- 更新是否保留前一版本；
- 删除是否传播到派生状态；
- 发生错误后是否能定位并回滚；
- 外部行动是否能追溯到具体状态和授权。

协议仍是试验性版本，作者没有声称 AOEP 已经是统一行业标准。它的贡献在于把治理从口号改写成了可记录、可比较的事件和状态检查。

## 8. 局限与启示

435 篇的编码语料是有范围的地图，不是完整普查；不同论文对“memory”“state”“agent”的定义也不完全相同。AOEP-v0 仍是 pilot，尚未覆盖所有生产环境的外部副作用、跨组织授权和对抗性恢复。

对工程实现而言，最直接的启示是：记忆记录至少要带 authority、scope、mutability、provenance、recoverability 和 actionability 六类字段或等价信息；评测要观察状态如何变化，而不能只在末尾问模型一个问题。
