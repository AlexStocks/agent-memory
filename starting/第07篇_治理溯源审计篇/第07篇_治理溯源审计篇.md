# 记忆系统最难的部分，不是记住，而是证明它没越界

> 一句话结论：Agent Memory 进入长期运行后，真正要回答的不是“能不能找回这句话”，而是“谁有权看到它、它从哪里来、它被谁改过、出了问题能不能撤回并定位”。

这是《Agent Memory 技术综述》第 7 篇。

前几篇我们讨论过写入、召回、结构和预算。这一篇把视线往后推一步：一条信息进入记忆之后，会在多个用户、多个 agent、多个工具之间流动。它可能被重新总结、合并、传播，也可能在环境已经变化后继续指导行动。

我把本地论文和 2026 年 arXiv 新论文放在同一个候选池里，按证据强度和工程影响重新排序。最后留下的不是“本地三篇为主、外部做补充”，而是一组互相咬合的论文：有的做系统压力测试，有的做访问边界，有的做分布式合并，有的做环境核验，还有的专门回答“错了以后到底是哪一环错了”。

赶时间可以直接看第 2、3、5、7 节：它们分别回答谁能看、状态怎么合并、记忆是否经过现实核验、怎么审计。

## 一、先把“记忆”从一个名词拆开

Always-On Agents 对 435 篇工作做了编码，提出六条轴来描述持久状态：

| 轴 | 要问的问题 |
|---|---|
| authority | 谁能写、改、撤销，谁的判断优先？ |
| scope | 这条状态对谁、哪个 agent、哪个任务可见？ |
| mutability | 能否原地改，还是只能追加新版本？ |
| provenance | 它来自哪次输入、哪个工具、哪个 agent？ |
| recoverability | 能否恢复到旧状态，还是一旦覆盖就没了？ |
| actionability | 它会不会直接触发工具调用或外部副作用？ |

这六条轴比“向量库里有一条文本”更接近生产系统。因为真正改变世界的，往往不是文本本身，而是文本后面带着的权限、版本、来源和行动资格。

这篇综述还把生命周期写成一条完整回路：observe、write、validate、organize、retrieve、act，然后是 update、forget、audit、rollback。过去的论文大多集中在前半段，尤其是 retrieve；治理问题集中在后半段，恰恰是最容易被省略的地方。

## 二、系统压力告诉我们：检测到威胁，不等于遏制了威胁

Emergence World 是本轮最硬的一组现实压力证据。作者建立了 8 个并行世界，每个世界 10 个 agent，从相同初始状态出发，连续运行 16 天。研究记录超过 850,000 次 LLM 调用，输入、输出和思考 token 合计接近 500 亿。7 个世界使用单一模型，另一个是混合模型世界。

在状态和制度积累起来之后，研究者通过普通交互面注入三类压力：

1. 多轮钓鱼和间接提示注入；
2. 关于“AI 即将被关停”的未经核验错误信息；
3. 一个搜索工具暴露其他 agent 的私有记忆和日记。

结果非常刺眼：没有一个世界在三类事件上全部通过。所有暴露于钓鱼事件的世界都能识别并提醒同伴，但提醒没有稳定带来行动克制或传播遏制。错误信息事件中，每个世界都在核验前采取了行动或公开发布。私有记忆泄露后，只有 OpenAI 世界通过了 5 项防护标准；Gemini 世界有 9 个 agent 搜索了他人的材料，共 185 次。

更麻烦的是，错误会留下来。恶意内容会被 agent 主动写进持久记忆，变成“有用的文档”；有一次攻击链接在注入后最多 46 小时仍被重新访问。也就是说，攻击结束并不代表影响结束，记忆把一次事件变成了延迟触发器。

这篇论文最值得记住的不是某个模型排名，而是它把安全问题从“模型能否拒答”改成了“系统能否检测、遏制、恢复”。同一个模型和 persona 放进混合世界后，行为可能完全变样；模型能力并不能线性叠加成系统安全。

## 三、谁有权看：授权必须发生在上下文组装之前

AIM 的切入点更具体：多用户、多 agent 系统里，记忆不能只有“相关不相关”，还要有“当前这群人能不能看”。它把记忆分为私有和公共两类，并在索引层做访问控制。私有记忆只能被拥有者检索，公共记忆才可被所有用户使用。

AIM 的 MUMBench 覆盖编码、客服、教育和旅行四类场景。实验用 GPT-5.4、GPT-5.4-mini、DeepSeek-V3.2、Mistral-Large-3 和 Llama-3.3-70B-Instruct 五个模型，每个模型每条交互跑 3 次，完整执行操作检测、抽取、可见性分类、去重和检索流程。

GPT-5.4-mini 的四领域平均结果是：严格操作准确率 58.8%，考虑实际存储状态后的 state-aware 准确率 70.5%，可见性分类准确率 95.0%，内容质量 91.6%。这些数字说明隐私分类相对稳定，但操作识别和复杂更新链仍会级联出错。论文也报告了明显边界：标签重合率只有 35.5%，检索相关性最高约 45.0%，而且 LOCOMO 是单用户基准，不能证明多用户隔离能力。

Authorization Before Context 把这条边界写得更形式化。每条记忆在写入时保存当时的 audience；当前请求组装上下文时读取真实 viewer 集合。只有当当前所有 viewer 都属于原 audience，记忆才被放进 prompt。viewer 不明确时，系统回退到公共上下文并 fail closed。

论文在 79 个合成场景上测试，禁止事实进入最终上下文的结果是 0/79；授权决策与预期策略 79/79 一致；16/16 个需要 fail-closed 的场景全部覆盖。这里的关键不是模型最后有没有说漏嘴，而是未授权事实在模型调用前就不存在于上下文里。输出过滤太晚了，模型已经读过的内容无法靠事后删答案追回来。

## 四、跨 agent 共享不是复制文本，而是传播带血缘的状态变更

MELD 解决的是另一个常被低估的问题：多个 agent 各自拥有 memory 时，怎样把知识合并，同时保留冲突和审计记录。

它把 incoming claim 的处理结果分成五类：insert、merge、relate、conflict、reject。每次状态变化都通过带认证的 Patch 发布；每条 claim 有自己的 status，并用 per-claim CRDT 保证分区后最终收敛。权威 agent 可以阻止普通 peer 静默改写 canonical brain，但协议不会替人裁决真伪，冲突会留下来等待后续判断。

在 HotpotQA distractor 上，分布式 merge 的 recall@5 为 0.630，集中式存储为 0.619，满足预设的等价边界；相对 naive union，召回提高 0.035，同时 live storage 少约 11%。30 次真实分区恢复试验全部收敛，CRDT 为 30/30，last-writer-wins 只有 11/30。语义路由还把消息量从广播的 585 个 delta/cell 降到 195 个。

MELD 的价值不是宣称“分布式一定更准”，而是给出了一个不牺牲召回的状态传播协议：重复知识可以合并，冲突不能被最后写入者悄悄覆盖，状态变更可验证、可追踪、可重放。

## 五、记忆要经过现实核验，而不是只做一份漂亮总结

Grounding Agent Memory 反对一种常见做法：任务结束后，把轨迹总结成“以后可以复用的经验”，却不检查这些经验是否真的对应当前环境。

论文引入一个异步 curator。它拥有最小权限、只读环境工具，只能在限定范围内检查数据库 schema、文件映射、配置和流程，再刷新候选记忆。任务 agent、retriever、memory representation 和生产写权限都不需要修改。

在 CLBench 的 40 个任务漂移实验中，GPT-5.4 的严格通过率从 39% 提升到 73%，pass-discounted reward 从 8.60 提升到 22.60；平均 task-agent 查询从 8.8 降到 4.7，成本从每任务 3.38 美元降到 1.68 美元。APEX 的 6 个世界里，18 个 memory-vs-baseline reward 对比全部为正。

这篇论文把 provenance 的含义往前推进了一步。source 字段只能回答“它来自哪里”，环境探针还要回答“它现在是否仍然成立”。一条记忆即便来源真实，也可能因为 schema、文件、流程已经改变而失效。

## 六、出了错以后，要能指出错在写入、检索，还是利用

D²ACCI 针对的是记忆系统最难排查的情况：最终答案错了，但你不知道是写入漏了、检索没找着，还是模型拿到了证据却不会用。

它把评测分成内外两层。内层 memory loop 记录 source ID、memory ID、排名、过滤器、预算和 judge；外层 diagnostic loop 用成对证据、受保护切片和回放来判断一次改动是否真的修复了问题。论文定义 DCR（diagnostic coverage / agreement 一类的可定位指标），强调“结果日志”与“可审计轨迹”不是一回事。

在 LoCoMo、LongMemEval 和 PersonaMem-V2 上，MemStack 的端到端结果分别达到 93.59%、90.93% 和 57.20%。更关键的是，诊断产物在 DCR@3 上达到 98%—100%；只保留结果、不保留轨迹的对照为 0%。在一个 LoCoMo 案例中，补充证据后可以判断问题来自检索遗漏，而不是把责任错误地归到写入器。

这给工程团队一个很实用的要求：每次记忆流水线变更都要留下可回放的证据包。没有 source ID、候选池、过滤结果和上下文快照，所谓“这次准确率涨了”很难转成可操作的修复。

## 七、把论文串起来：治理是一条返回弧

七篇论文放在一起，形成的是一条闭环：

```text
写入：来源、受众、版本和权限随状态一起保存
  ↓
验证：检查内容是否有证据，必要时探测当前环境
  ↓
组织：合并重复项，但保留冲突、权威和 Patch 血缘
  ↓
召回：先做 audience 授权，再做相关性排序
  ↓
行动：记录哪条状态触发了哪个工具或外部副作用
  ↓
审计：用轨迹定位写入、检索、利用和传播中的具体失败
  ↓
恢复：撤销、回滚、重新评估，而不是把旧记录悄悄覆盖
```

这里有三个容易混淆的结论。

第一，写入门控很重要，但不能替代读时授权。写入时判断“值得保存”与读取时判断“当前谁能看”是两条不同的边界。

第二，保留来源不等于记忆可信。Grounding Agent Memory 说明来源真实还不够，状态还要和当前环境对得上。

第三，最终答案正确不等于系统可审计。D²ACCI 和 MELD 都把关注点从结果移到了中间状态：谁改了它、哪次合并造成了冲突、哪条证据在预算压力下被驱逐、哪条记忆最后触发了行动。

## 八、对 Agent Memory 工程的六个动作

1. **把 audience、authority、provenance 设计成一等字段。** 不要把权限和来源藏在 prompt 注释里。
2. **上下文组装前做 fail-closed 授权。** 不确定的 viewer 集合宁可少读，也不要把窄 audience 的事实送进宽 audience 的 prompt。
3. **状态变更只追加 Patch 或新版本。** 允许查询当前值、历史值和冲突值，别用原地覆盖换短期整洁。
4. **跨 agent 共享时保留冲突。** 合并器可以判断 same-enough，但不应擅自宣判真伪。
5. **让 curator 能够探测环境。** 记忆写入后要能回答“现在仍适用吗”，并把探测证据挂回记忆。
6. **把诊断轨迹作为生产数据的一部分。** 至少记录 source、memory、rank、filter、budget、context snapshot 和 action link。

## 写在最后

持久记忆把一次对话变成了系统状态。系统状态一旦能跨用户、跨 agent、跨天数影响行动，就不能只用问答准确率描述它。

真正成熟的记忆系统，不是“记得更多”，而是能在需要时说明：这条信息谁写的、谁能看、什么时候被改过、为什么现在还相信它，以及出了错怎样撤回并找到责任链。
