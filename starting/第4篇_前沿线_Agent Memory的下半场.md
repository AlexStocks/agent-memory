# Agent Memory 的下半场：从记住信息到自我进化

Agent Memory 下一阶段的分水岭已经很清楚：系统能否学会何时写、何时读、怎样更新，以及什么时候遗忘。

前面三篇写完以后，我原本以为这套 Agent Memory 梳理可以收尾了。

结果 2026 年又来了两篇综述。一篇只有 15 页，试图把记忆系统写成一个工程闭环；另一篇足足 90 页，60 位作者整理了 218 篇论文。

两篇论文一短一长，最后都把问题指向了记忆管理策略。

> **赶时间？** 第四节是两篇论文的交叉结论，第五节是我认为工程上最该落地的五件事。

这篇文章是前三篇之后的独立更新，不要求读者先把前文全部看完。涉及的两篇论文分别是：

- Pengfei Du，*Memory for Autonomous LLM Agents: Mechanisms, Evaluation, and Emerging Frontiers*，arXiv:2603.07670；
- Wei-Chieh Huang 等，*A Survey of Agent Memory in the Second Half: Towards Self-Evolving and Long-Horizon Agents*，arXiv:2602.06052，TMLR 2026。

第二篇论文需要先做一个题名校正。它的正式题名不是网上流传的 “Rethinking Memory Mechanisms”，而是 **A Survey of Agent Memory in the Second Half**。本文按 arXiv `v4`（2026-08-04）讨论。

## 一、为什么还需要两篇新的记忆综述

2023 年前后，Agent Memory 的问题相对直白。

上下文窗口不够，就把历史放到外部存储；需要的时候，再用向量检索找回来。Generative Agents 加入 memory stream 和 reflection，MemGPT 把上下文类比成内存，把外部存储类比成磁盘。后来的 Mem0、Zep、A-MEM，则分别向事实抽取、时间知识图和自组织记忆扩展。

这些工作解决了很多“怎么存”的问题，但生产中的麻烦往往发生在存储前后：

- 一句话到底值不值得长期保存？
- 新事实和旧事实矛盾时，是覆盖、失效，还是并存？
- 检索到了正确内容，agent 为什么仍然做错？
- 多个 agent 共用记忆时，谁能写，谁来处理冲突？
- 用户要求删除以后，向量、摘要、图、缓存和模型参数里的影响怎么清掉？

两篇 2026 综述都把视线从 memory store 往外移。存储只占其中一环，控制策略、行动结果、成本和治理开始进入同一张图。

![图 1：基础智能体记忆路线图，论文汇总了 2023—2025 年的代表性工作](images/AgentMemorySecondHalf/01-roadmap.png)

这也是它们适合单独成篇的原因。前三篇讲的是经典论文、开源实现和工程治理；这两篇更像一次阶段复盘，告诉我们整个领域在 2026 年把问题推进到了哪里。

## 二、第一篇：把记忆写成一个决策闭环

`2603.07670` 的核心贡献是一个简洁的形式化。

在第 $t$ 步，agent 收到输入 $x_t$，从当前记忆 $M_t$ 中读取相关内容，再结合目标 $g_t$ 产生动作：

$$
a_t = \pi_\theta\bigl(x_t,\mathcal{R}(M_t,x_t),g_t\bigr)
$$

动作执行以后，环境返回观测 $o_t$ 和可能的奖励信号 $r_t$，系统再更新记忆：

$$
M_{t+1}=\mathcal{U}(M_t,x_t,a_t,o_t,r_t)
$$

第二个公式决定了这套系统与普通检索库的差别。

$\mathcal{U}$ 负责完整的记忆管理：过滤闲聊、统一日期和名称、合并重复内容、给记忆打优先级、处理矛盾，并决定哪些东西应该删除。

于是，记忆形成了一个反馈回路：

```text
输入 → 读取记忆 → 决策 → 行动执行 → 获得反馈 → 更新记忆
             ↑                              ↓
             └──────── 下一轮继续使用 ────────┘
```

一次错误回答只影响当前轮。一次错误写入可能影响后面几十轮，因为未来的决策会继续把它当成历史事实。

### 2.1 三个维度，别再把所有问题都归给向量库

论文用三个正交维度组织 Agent Memory：

| 维度 | 它回答什么 | 主要类型 |
|---|---|---|
| 时间范围 | 这段记忆服务多长时间 | 工作、情节、语义、程序记忆 |
| 表示载体 | 记忆以什么形式存在 | 上下文文本、向量索引、结构化存储、可执行仓库、混合存储 |
| 控制策略 | 谁决定写、读和忘 | 启发式、prompt 驱动、学习式策略 |

这三个维度经常被混为一谈。

例如，一段“以后遇到这个错误，先检查代理配置”的经验，认知上属于程序记忆；它可以保存在 Markdown、向量库或代码仓库里；至于它由人审核后写入，还是由 agent 自动总结，又是控制策略的问题。

只讨论“向量还是图”，最多回答了表示载体。它没有回答记忆的用途，也没有回答谁拥有修改权。

### 2.2 评价记忆，不能只看 Recall@K

Precision@$k$ 和 nDCG 可以告诉我们检索器有没有找到正确文档，却不能回答 agent 是否正确使用了它。

论文建议把评估拆成四层：

1. **任务效用**：任务是否完成，事实是否正确，计划是否落地；
2. **记忆质量**：相关事实有没有召回，是否陈旧，是否互相矛盾；
3. **效率**：每次操作增加多少延迟、token 和存储；
4. **治理**：有没有越权读取，删除是否完整，敏感数据是否泄漏。

这个变化很关键。过去的测试更像闭卷问答：“你还记得用户三个月前说过什么吗？”真实 agent 面对的是连续任务：“你能不能利用三个月前的约束，把今天的事情正确做完？”

论文引用 MemoryArena 的结果说明，一些在 LoCoMo 上接近饱和的模型，放进相互依赖的多会话任务以后会下降到 40%—60%。这个数字不能脱离具体模型和实验配置横向使用，但它说明了问题：**会回答记忆题，不等于会在行动中使用记忆。**

### 2.3 这篇论文的边界

它只有 15 页，作者只有一位，目前仍是 `v1`。

它适合当工程检查表，不适合替代对每个系统和 benchmark 的原始论文核验。论文摘要称分析“五类机制”，正文第 4 节实际列出六个小节，额外包含 parametric memory 和基于权重的适应。这个计数差异也说明，综述本身同样需要被审阅，而不是被当成新的标准答案。

## 三、第二篇：60 位作者画了一张 218 篇论文的地图

如果说第一篇在回答“记忆系统应该怎样运转”，`2602.06052` 更关心“整个领域现在应该怎样组织”。

论文筛选了 2023 年第一季度至 2025 年第四季度的 218 篇工作，并沿三个维度分类：Memory Substrate、Cognitive Mechanism 和 Memory Subject。

![图 2：基础智能体记忆的三维分类](images/AgentMemorySecondHalf/02-memory-main.png)

### 3.1 Memory Substrate：记忆究竟存在哪里

论文先把载体分成内部与外部。

外部记忆包括向量索引、文本记录、关系表、知识图和分层存储。它容易查看、修改和删除，也能跨会话扩展，但每次使用都要付出检索、重排和上下文注入的成本。

内部记忆包括模型权重、latent state 和 KV cache。它与模型推理结合得更紧，访问速度也快，但更新、审计和定点删除困难。尤其当知识进入模型参数以后，“删除一条用户记忆”就不再是删一行数据库记录。

这里没有哪个载体全面胜出。工程系统大多会混合使用：热状态留在当前上下文，长期事件放外部存储，稳定能力可能通过微调或 adapter 内化。

### 3.2 Cognitive Mechanism：这段记忆是拿来干什么的

论文采用五类认知记忆：

- 感觉记忆：短暂保留视觉、音频和传感输入；
- 工作记忆：维护当前任务正在处理的状态；
- 情节记忆：保存具体发生过的交互和事件；
- 语义记忆：从多次经验中抽象出事实与概念；
- 程序记忆：保存“应该怎样做”的技能和流程。

这五类记忆描述的是一条连续的处理链。

短期系统决定什么信息进入处理流程，长期系统把经验沉淀成知识和技能。理想情况下，一次失败先成为情节记录，多次相似失败再形成语义判断，最终沉淀成可以复用的程序技能。

现实中的系统通常只做好其中两层。情节如何升级成语义，语义如何变成程序，中间仍然大量依赖 prompt 和定时总结。

### 3.3 Memory Subject：记忆到底属于谁

这是 2024 年之前的综述较少单独强调的一层。

**User-centric memory** 服务个性化。它保存用户偏好、关系、长期目标和历史承诺。正确答案会随用户和时间变化。

**Agent-centric memory** 服务 agent 自己。它保存任务经验、失败路径、工具使用策略和环境状态，目标是提高下一次执行质量。

一个 coding agent 可以同时拥有两者：用户偏好“提交信息用中文”属于 user-centric semantic memory；过去三次 Windows 构建都因为同一个路径问题失败，则属于 agent-centric episodic memory，进一步还可能沉淀成程序记忆。

如果系统不区分主体，就很容易把个人偏好变成全局规则，或者把一个 agent 的错误经验传播给所有 agent。

### 3.4 多智能体还要解决共享之外的问题

论文把单智能体的操作归纳为存储与索引、加载与检索、更新与刷新、压缩与总结、遗忘与保留五类。

到了多智能体系统，还要再回答三组问题：

- 采用 private-only、shared workspace、hybrid 还是 orchestrated 架构；
- 记忆由 orchestrator 路由、agent 主动读取，还是由记忆内容触发；
- 并发写入如何隔离，矛盾如何合并，错误由谁纠正。

共享向量库只能说明数据放在同一个地方。它没有说明所有权、访问范围、一致性和责任归属。

## 四、两篇论文放在一起，出现了五个明显变化

两篇论文篇幅相差六倍，组织方式也不一样，但结论高度一致。

| 变化 | 过去常见的做法 | 2026 年综述强调的方向 |
|---|---|---|
| 存储 → 策略 | 设计一个向量库或图数据库 | 学习何时写、读、更新和遗忘 |
| 召回 → 行动 | 用问答准确率测试“记得多少” | 看记忆是否改善长期任务完成 |
| 单体 → 多体 | 每个 agent 管自己的历史 | 处理共享、隔离、路由和冲突 |
| 容量 → 预算 | 上下文越长、存得越多越好 | 在有限 token、延迟和成本下选择 |
| 功能 → 治理 | 关注能不能存和搜 | 同时验证来源、权限、删除和审计 |

### 4.1 记忆从数据结构变成了控制系统

过去我们容易把 Agent Memory 理解成 RAG 的一个变体：多一个数据库，多一次检索，再把结果塞回 prompt。

两篇论文都把重点放在控制策略上。agent 要决定何时写、写成哪种形式、什么时候搜索、如何合并、何时遗忘。每一个决定都会影响未来状态。

它已经是一个持续运行的控制系统，远比被动查询接口复杂。

![图 4：记忆演化与优化策略，覆盖 prompt、微调和强化学习](images/AgentMemorySecondHalf/06-learned-policy.png)

### 4.2 长上下文没有让记忆消失

更长的上下文扩大了工作记忆，却没有提供跨会话持久性、事实版本、选择性检索和删除语义。

把十万 token 历史全部塞进去，也不代表模型能稳定找到中间那条关键约束。更现实的组合仍然是：适量上下文保存当前状态，外部记忆保存长期事实，再通过有预算的检索组装本轮 Context Pack。

长上下文解决“这一轮能看多少”，外部记忆解决“跨时间保存什么，以及何时取回来”。两者需要配合使用。

### 4.3 Forgetting 开始从缺陷变成能力

早期系统把遗忘理解成容量不足后的被动丢弃。新综述把选择性遗忘视为长期 agent 的基本能力。

过时地址、已经撤销的权限、失效的工作流程，如果一直排在检索结果前面，会持续污染决策。另一方面，医疗过敏史、安全约束和合同承诺又不能被粗暴压缩掉。

系统需要按来源、时间、风险和长期效用决定忘什么，同时保留可审计的变更历史。

### 4.4 Benchmark 开始检验行动中的记忆

`2602.06052` 把 benchmark 分成 user-centric 和 agent-centric 两组。

前者测多会话个性化、事实更新、时间推理、压缩、遗忘和 abstention。后者把记忆放进 Web、桌面、代码、机器人、游戏和科研任务，观察 agent 能不能保持状态并完成行动。

两组不能互相代替。LoCoMo 得分高，不能推出 SWE-bench、WebArena 或 OSWorld 中的长期执行也可靠。一个系统也可能很会维护用户画像，却不会从自己的失败轨迹中学习。

### 4.5 治理进入记忆的完整生命周期

一旦记忆跨会话保存，隐私和权限问题就从 prompt 层进入数据生命周期。

系统至少要记录谁写入、来源是什么、适用哪个 scope、何时生效、何时失效、谁读过，以及删除后清理了哪些投影。

如果记忆已经参与微调或写入参数，普通数据库删除甚至不够。机器遗忘仍远未成为成熟的生产方案，这也是内部记忆必须谨慎使用的原因。

## 五、工程上最该落地的五件事

读完两篇论文，我认为没有必要立刻给系统加一个更复杂的图数据库，也不用先训练记忆策略模型。

更应该先补下面五件事。

### 5.1 原始事件与派生记忆分开

消息、文档、工具结果和环境观测应当作为可重放的原始 episode 保存。事实条目、摘要、embedding 和图关系都是派生结果。

抽取器升级或者 schema 改变以后，派生层应该能够从原始层重建。否则一次错误总结会永久变成“事实”。

### 5.2 给记忆加上时间、来源和作用域

一条记忆至少需要回答：谁说的、什么时候发生、系统什么时候写入、适用于哪个用户或 agent、由哪一版抽取器生成。

“用户使用 PostgreSQL”如果来自三年前，不一定能覆盖今天的明确选择。判断当前事实必须使用时间和来源，不能把它们当成可选 metadata。

### 5.3 把 write/read/forget 全部记录下来

错误答案可能来自四个地方：该写的没有写、写入内容错了、读取找错了，或者模型拿到正确内容后仍然推理错了。

没有记忆操作日志，这四类问题看起来都像“模型偶尔抽风”。至少应记录每次写入、检索、更新、失效和删除涉及的内容与触发上下文。

### 5.4 同时测试召回和任务完成

记忆测试不能停在“相关文档排第几”。还要验证 agent 是否使用了正确版本，是否遵守其中的约束，是否避免重复副作用，以及 context 压缩后能否继续执行。

对 coding agent 来说，恢复以后重复 push、重复发布，或者把“计划执行”误记成“已经执行”，比忘记一段普通对话危险得多。

### 5.5 自动学习之前，先建立审批和回滚

让 agent 自动总结偏好风险不算高；让它自动修改组织规则、安全策略或程序记忆，风险完全不同。

新的经验可以先进入待审区。只有经过重复证据、自动评估或人工批准，才提升为长期事实、全局指令或可执行 skill。所有提升都要有 revision 和回滚入口。

## 六、别把两篇综述当成排行榜

`2603.07670` 的优势是短、清楚、工程导向。它把记忆闭环、评估层次和生产模式连在了一起。它的局限同样明显：当前是单作者 `v1`，篇幅有限，许多数字来自被引用论文，并非重新复现。

`2602.06052` 的优势是覆盖广。90 页、60 位作者、218 篇论文、6 张大表，适合作为研究地图。覆盖越广，每个项目能得到的审查深度就越有限。表格中标记某个 benchmark“覆盖”某项能力，也不等于所有系统已经在统一模型和硬件上完成横向测试。

| 论文 | 最适合用来做什么 | 不应该拿来做什么 |
|---|---|---|
| `2603.07670` | 设计记忆闭环、指标和工程检查表 | 直接证明某个项目性能最好 |
| `2602.06052` | 查领域地图、分类、benchmark 和研究方向 | 把 218 篇工作当成统一复现实验 |

两篇论文最好一起读。前者告诉你一个记忆系统应该有哪些环节，后者告诉你这些环节在整个研究版图里处于什么位置。

## 写在最后

Agent Memory 的第一阶段，大家在解决“模型怎样记住窗口之外的信息”。这个问题还没有彻底解决，但已经有了向量检索、事实抽取、分层上下文和时间知识图等一批可用方案。

下一阶段更难。agent 要在长期运行中判断什么值得记，如何面对冲突，什么时候应该忘记，以及怎样证明自己没有读错、写错或删漏。

存得更多不会自动带来更好的 agent。工程上的分水岭，是系统能否在正确的时候拿到正确版本的信息，并在错误发生以后解释、撤销和重建。
