## 摘要

我们提出 **Zep**，一种面向 AI 智能体的新型记忆层服务，在 Deep Memory Retrieval（DMR，深度记忆检索）基准上超越了当前最先进的系统 MemGPT。此外，在比 DMR 更全面、更具挑战性、也更贴近真实企业应用场景的评测中，Zep 同样表现优异。

现有的、面向大语言模型（LLM）智能体的检索增强生成（RAG）框架局限于**静态文档检索**，而企业应用要求从多种来源动态整合知识——包括正在进行的对话和业务数据。Zep 通过其核心组件 **Graphiti** 来化解这一根本局限：Graphiti 是一个**时序感知（temporally-aware）的知识图谱引擎**，能够动态综合非结构化的对话数据与结构化的业务数据，同时维护历史关系。

在 MemGPT 团队确立为其主要评测指标的 DMR 基准上，Zep 表现出更优性能（**94.8% vs 93.4%**）。除 DMR 之外，Zep 的能力还在更具挑战性的 **LongMemEval** 基准上得到验证——该基准通过复杂的时序推理任务更好地反映企业用例。在这一评测中，Zep 取得了显著结果：准确率最高提升 **18.5%**，同时将响应延迟相比基线实现降低了 **90%**。这些结果在**跨会话信息综合**与**长期上下文维持**等企业关键任务上尤为突出，证明了 Zep 在真实应用部署中的有效性。

## 1. 引言

基于 Transformer 的大语言模型（LLM）对产业界和研究界的影响近年来备受关注 `[1]`。LLM 的一个重要应用方向是开发**对话式智能体**。然而，这些智能体的能力受限于 LLM 的上下文窗口、有效上下文利用率，以及预训练阶段所获得的知识。因此，需要额外的上下文来提供**域外（out-of-domain, OOD）知识**并减少幻觉。

检索增强生成（RAG）已成为 LLM 应用中的一个关键方向。RAG 借用了过去五十年间开创的信息检索（IR）技术 `[2]`，为 LLM 提供必要的领域知识。

当前的 RAG 方法聚焦于**宽泛的领域知识**和**基本静态的语料**——也就是说，加入语料的文档内容很少变化。然而，若智能体要普及到我们的日常生活中、自主地解决从琐碎到高度复杂的各种问题，它们将需要访问一个**持续演进的大规模数据语料**，这些数据来自用户与智能体的交互，以及相关的业务数据和世界数据。我们认为，赋予智能体这种广泛而动态的"记忆"，是实现这一愿景的关键基石；并且我们主张，**当前的 RAG 方法并不适合这一未来场景**。由于完整的对话历史、业务数据集以及其他领域专属内容无法有效地塞进 LLM 的上下文窗口，必须为智能体记忆开发新的方法。给 LLM 驱动的智能体加上记忆并非新想法——这一概念此前已在 MemGPT `[3]` 中被探索过。

近来，知识图谱（KG）被用于增强 RAG 架构，以解决传统 IR 技术的诸多不足 `[4]`。本文我们介绍 **Zep** `[5]`——一个由 **Graphiti** `[6]`（一个动态的、时序感知的知识图谱引擎）驱动的记忆层服务。Zep 摄取并综合**非结构化的消息数据**与**结构化的业务数据**。Graphiti 知识图谱引擎以**非损（non-lossy）**的方式用新信息动态更新知识图谱，维护事实与关系的时间线，包括它们的**有效期（periods of validity）**。这种方式使知识图谱能够表征一个复杂且不断演进的世界。

由于 Zep 是一个生产系统，我们在其记忆检索机制的**准确率、延迟和可扩展性**上投入了大量精力。我们使用两个已有基准来评估这些机制的有效性：来自 MemGPT `[3]` 的 Deep Memory Retrieval 任务（DMR），以及 LongMemEval 基准 `[7]`。

## 2. 知识图谱构建

在 Zep 中，记忆由一个时序感知的动态知识图谱 𝒢 = (𝒩, ℰ, φ) 驱动，其中 𝒩 表示节点，ℰ 表示边，φ: ℰ → 𝒩 × 𝒩 表示形式化的关联函数。该图谱包含**三个层级的子图**：**情节（episode）子图**、**语义实体（semantic entity）子图**和**社群（community）子图**。

- **情节子图 𝒢ₑ**：情节节点（episodes，记作 nᵢ ∈ 𝒩ₑ）以消息、文本或 JSON 的形式保存原始输入数据。情节充当**非损数据存储**，从中抽取语义实体与关系。情节边（eᵢ ∈ ℰₑ ⊆ φ*(𝒩ₑ × 𝒩ₛ)）把情节连接到它所引用的语义实体。
- **语义实体子图 𝒢ₛ**：语义实体子图构建在情节子图之上。实体节点（entities，nᵢ ∈ 𝒩ₛ）表示从情节中抽取出来、并与图中已有实体做过消解（resolved）的实体。实体边（语义边，eᵢ ∈ ℰₛ ⊆ φ*(𝒩ₛ × 𝒩ₛ)）表示从情节中抽取出的实体之间的关系。
- **社群子图 𝒢𝒸**：社群子图构成 Zep 知识图谱的最高层次。社群节点（communities，nᵢ ∈ 𝒩𝒸）表示**强连通实体的聚类**。社群包含对这些聚类的高层摘要，代表对 𝒢ₛ 结构的一种更全面、更互相关联的视图。社群边（eᵢ ∈ ℰ𝒸 ⊆ φ*(𝒩𝒸 × 𝒩ₛ)）把社群连接到其成员实体。

同时存储**原始情节数据**与**派生的语义实体信息**，这种做法映照了人类记忆的心理学模型。这些模型区分**情节记忆**（表征一个个独立的事件）与**语义记忆**（捕捉概念之间的关联及其含义）`[8]`。这种方式使使用 Zep 的 LLM 智能体能够发展出更精细、更微妙的记忆结构，更贴合我们对人类记忆系统的理解。知识图谱为表征这些记忆结构提供了有效的媒介，我们对**独立的情节子图与语义子图**的实现借鉴了 AriGraph `[9]` 中的类似做法。

我们使用社群节点来表征高层结构与领域概念，这一做法建立在 GraphRAG `[4]` 的工作之上，使对领域更全面的**全局理解**成为可能。由此形成的层级组织——从情节到事实、到实体、再到社群——扩展了已有的层级化 RAG 策略 `[10][11]`。

### 2.1 情节（Episodes）

Zep 的图谱构建始于摄取称为 **Episodes（情节）** 的原始数据单元。情节可以是三种核心类型之一：**message（消息）**、**text（文本）**或 **JSON**。虽然每种类型在图谱构建期间都需要特定的处理，但本文聚焦于 message 类型，因为我们的实验以**对话记忆**为中心。在我们的语境下，一条消息由相对较短的文本（若干条消息可以放进一个 LLM 上下文窗口）以及产生这段话的关联**说话者（actor）**组成。

每条消息都带有一个**参考时间戳 t_ref**，指示消息发出的时间。这一时间信息使 Zep 能够准确识别并抽取消息内容中提到的相对或部分日期（例如"下周四"、"两周内"或"去年夏天"）。Zep 实现了一种**双时态（bi-temporal）模型**：时间线 **T** 表示事件的时序顺序，时间线 **T′** 表示 Zep 数据摄取的事务顺序。T′ 时间线承担数据库审计的传统用途，而 T 时间线则为建模对话数据与记忆的动态本质提供了一个额外维度。这一双时态方法代表了基于 LLM 的知识图谱构建中的一项新颖进展，也是 Zep 相较以往基于图的 RAG 方案诸多独特能力的基础。

情节边 ℰₑ 把情节连接到它们抽取出的实体节点。情节及其派生的语义边维护**双向索引**，追踪边与其源情节之间的关系。这一设计强化了 Graphiti 情节子图的非损本质，支持**前向和后向遍历**：语义产物可以溯源到它们的出处以便引用或引述，而情节也可以快速检索到其相关实体与事实。虽然本文的实验并不直接考察这些连接，但它们将在未来的工作中被探索。

### 2.2 语义实体与事实

#### 2.2.1 实体

实体抽取（entity extraction）代表情节处理的初始阶段。在摄取期间，系统同时处理**当前消息内容**和**最近 n 条消息**，为命名实体识别提供上下文。在本文以及 Zep 的通用实现中，**n = 4**，即提供两个完整的对话轮次用于上下文评估。由于我们聚焦于消息处理，**说话者会被自动抽取为一个实体**。在初始实体抽取之后，我们采用一种受 reflexion `[12]` 启发的**反思（reflection）技术**，以尽量减少幻觉并提升抽取覆盖率。系统还从情节中抽取**实体摘要**，以便后续的实体消解与检索操作。

抽取完成后，系统把每个实体名称嵌入到一个 **1024 维向量空间**中。该嵌入使得可以通过对图中已有实体节点做**余弦相似度搜索**来检索相似节点。系统还对已有的实体名称与摘要执行一次单独的**全文搜索**，以识别额外的候选节点。这些候选节点连同情节上下文一起，通过我们的实体消解提示词交由 LLM 处理。当系统识别出重复实体时，会生成一个**更新后的名称与摘要**。

在实体抽取与消解之后，系统使用**预定义的 Cypher 查询**把数据写入知识图谱。我们选择这一做法而非让 LLM 生成数据库查询，是为了确保**模式格式一致**，并减少幻觉的可能性。

抽取完成后，系统为事实生成嵌入，为写入图谱做准备。系统通过一个类似于实体消解的过程执行**边去重（edge deduplication）**。面向相关边的混合搜索被**限制在"与待新增边连接同一对实体"的那些边**上。这一约束不仅防止了不同实体之间相似边的错误组合，还通过把搜索空间限定到与该特定实体对相关的一个边子集，显著降低了去重过程的计算复杂度。

#### 2.2.3 时间抽取与边失效（Edge Invalidation）

Graphiti 相较其他知识图谱引擎的一个关键差异化特性，是它通过**时间抽取**与**边失效**流程来管理能力动态更新的信息。

系统利用 t_ref 从情节上下文中抽取关于事实的时间信息。这使得系统能够准确抽取并以 datetime 表示**绝对时间戳**（例如 "Alan Turing was born on June 23, 1912"）和**相对时间戳**（例如 "I started my new job two weeks ago"）。与我们的双时态建模方法一致，系统追踪**四个时间戳**：**t′_created** 与 **t′_expired ∈ T′** 监控事实在系统中何时被创建或失效；**t_valid** 与 **t_invalid ∈ T** 则追踪事实成立的真实时间区间。这些时间数据点连同其他事实信息一起存储在边上。

新边的引入可能使数据库中的已有边失效。系统使用一个 LLM 把新边与语义相关的已有边进行比较，以识别潜在矛盾。当系统识别出**时间上重叠的矛盾**时，就通过把受影响边的 **t_invalid 设为使其失效的那条边的 t_valid** 来令其失效。遵循事务时间线 T′，Graphiti 在判断边失效时**始终优先采信新信息**。

这一整套方法使得 Graphiti 能够随着对话演进而动态添加数据，同时既维护**当前的关系状态**，也维护**关系随时间演化的历史记录**。

### 2.3 社群（Communities）

在建立情节子图与语义子图之后，系统通过**社群检测**构建社群子图。我们的社群检测方法建立在 GraphRAG `[4]` 描述的技术之上，但我们采用的是**标签传播算法（label propagation）** `[13]`，而非 Leiden 算法 `[14]`。这一选择是因为标签传播具有**直观的动态扩展方式**，使系统能够在新数据进入图谱后，在更长时间内维持准确的社群表征，从而推迟完全重建社群的需要。

该动态扩展实现了标签传播中**单个递归步骤**的逻辑：当系统向图中加入一个新的实体节点 nᵢ ∈ 𝒩ₛ 时，它会考察邻居节点所属的社群；系统把这个新节点分配给其邻居中**占多数（plurality）**的那个社群，然后相应更新社群摘要和图。虽然这种动态更新使得数据流入系统时能够高效扩展社群，但由此得到的社群会逐渐偏离一次完整标签传播运行所生成的社群。因此，**周期性的社群重建仍然是必要的**。不过，这一动态更新策略提供了一个实用的启发式方法，显著降低了延迟和 LLM 推理成本。

沿用 `[4]`，我们的社群节点包含通过对成员节点做**迭代式 map-reduce 摘要**得到的摘要。然而，**我们的检索方法与 GraphRAG 的 map-reduce 方法有实质性差异** `[4]`。为了支持我们的检索方法，我们生成包含关键术语与相关主题的**社群名称**（community names）。这些名称被嵌入并存储，以支持余弦相似度搜索。

## 3. 记忆检索

Zep 中的记忆检索系统提供强大、复杂且高度可配置的功能。在高层次上，Zep 的图搜索 API 实现一个函数 **f: S → S**，它接受一个文本串查询 α ∈ S 作为输入，返回一个文本串上下文 β ∈ S 作为输出。输出 β 包含节点与边的格式化数据，供 LLM 智能体针对查询 α 生成准确的响应。过程 f(α) → β 由**三个不同的步骤**组成：

- **搜索（Search, φ）**：流程始于识别可能包含相关信息的候选节点与边。Zep 采用多种不同的搜索方法，整体搜索函数可表示为 φ: S → ℰₛⁿ × 𝒩ₛⁿ × 𝒩𝒸ⁿ。也就是说，φ 把一个查询变换为一个三元组，其中包含语义边、实体节点、社群节点的列表——这三类图对象包含了相关的文本信息。
- **重排序（Reranker, ρ）**：第二步对搜索结果重新排序。重排序函数或模型接受一个搜索结果列表，产生这些结果的一个重排版本：ρ: φ(α), … → ℰₛⁿ × 𝒩ₛⁿ × 𝒩𝒸ⁿ。
- **构造器（Constructor, χ）**：最后一步，构造器把相关的节点与边变换为文本上下文：χ: ℰₛⁿ × 𝒩ₛⁿ × 𝒩𝒸ⁿ → S。对每个 eᵢ ∈ ℰₛ，χ 返回 fact 以及 t_valid、t_invalid 字段；对每个 nᵢ ∈ 𝒩ₛ，返回 name 与 summary 字段；对每个 nᵢ ∈ 𝒩𝒸，返回 summary 字段。

有了这些定义，我们可以把 f 表达为这三个组件的复合：**f(α) = χ(ρ(φ(α))) = β**。

```text
FACTS and ENTITIES represent relevant context to the current conversation.
These are the most relevant facts and their valid date ranges. If the fact is about an event,
the event takes place during this time.
format: FACT (Date range: from - to)
<FACTS>
{facts}
</FACTS>
These are the most relevant entities
ENTITY_NAME: entity summary
<ENTITIES>
{entities}
</ENTITIES>
```

### 3.1 搜索

Zep 实现三种搜索函数：**余弦语义相似度搜索（φ_cos）**、**Okapi BM25 全文搜索（φ_bm25）**和**广度优先搜索（φ_bfs）**。前两个函数使用 Neo4j 的 Lucene 实现 `[15][16]`。每种搜索函数在识别相关文档时提供不同的能力，它们共同在重排序之前提供对候选结果的全面覆盖。**搜索字段因对象类型而异**：对 ℰₛ 搜索 fact 字段；对 𝒩ₛ 搜索实体名称；对 𝒩𝒸 搜索社群名称（由社群涵盖的关键词与短语组成）。虽然我们是独立开发的，但我们的社群搜索方法与 LightRAG `[17]` 中的高层关键词搜索方法类似。把 LightRAG 的方法与 Graphiti 这类基于图的系统相融合，是未来研究的一个有前景的方向。

虽然余弦相似度和全文搜索方法在 RAG 中已经确立 `[18]`，但**在知识图谱上做广度优先搜索**在 RAG 领域受到的关注有限，值得注意的例外是 AriGraph `[9]` 和 Distill-SynthKG `[19]` 这类基于图的 RAG 系统。在 Graphiti 中，广度优先搜索通过识别 **n 跳内**的额外节点与边来增强初始搜索结果。此外，φ_bfs 可以接受**节点作为参数**，从而对搜索函数有更强的控制力。当使用**最近的情节**作为广度优先搜索的种子时，这一功能尤其有价值，使系统能够把最近提及的实体与关系纳入检索到的上下文。

三种搜索方法各自针对相似性的不同方面：**全文搜索**识别词语相似性，**余弦相似度**捕捉语义相似性，**广度优先搜索**揭示上下文相似性——即在图中更靠近的节点与边倾向于出现在更相似的对话上下文中。这种多面向的候选结果识别方式，最大化了发现最优上下文的可能性。

### 3.2 重排序（Reranker）

初始搜索方法的目标是实现**高召回率**，而重排序器则通过把最相关的结果排在前面来提升**精确率**。Zep 支持已有的重排序方法，如 **Reciprocal Rank Fusion（RRF）** `[20]` 和 **Maximal Marginal Relevance（MMR）** `[21]`。此外，Zep 实现了一个**基于图的"情节提及"重排序器（episode-mentions reranker）**，它根据实体或事实在一段对话中被提及的频率来给结果排序，从而实现"被频繁引用的信息变得更容易被取用"的机制。系统还包括一个**节点距离重排序器（node distance reranker）**，它根据结果到指定**中心节点**的图距离重新排序，提供聚焦于知识图谱特定区域的上下文。系统最复杂的重排序能力采用 **cross-encoder（交叉编码器）**——用交叉注意力机制对节点与边相对查询进行打分以生成相关性分数的 LLM，不过这一方法的计算成本也最高。

## 4. 实验

本节分析使用基于 LLM 记忆的基准所做的两项实验。第一项评测采用 `[3]` 中提出的 **Deep Memory Retrieval（DMR）** 任务，它使用 Multi-Session Chat 数据集的一个 500 段对话子集，该数据集出自《Beyond Goldfish Memory: Long-Term Open-Domain Conversation》`[22]`。第二项评测采用出自《LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory》的 **LongMemEval 基准** `[7]`。具体而言，我们使用 **LongMemEvalₛ** 数据集，它提供的对话上下文平均长达 **115,000 token**。

在两项实验中，我们都通过 Zep 的 API 把对话历史写入 Zep 知识图谱。然后，使用第 3 节描述的技术检索**最相关的 20 条边（事实）和实体节点（实体摘要）**。系统把这些数据重新格式化为一个上下文字符串，与 Zep 记忆 API 提供的功能相对应。

虽然这些实验展示了 Graphiti 的关键检索能力，但它们只代表了系统完整搜索功能的一个子集。这一聚焦的范围使得与已有基准的清晰比较成为可能，同时把对知识图谱其他能力的探索留给未来的工作。

### 4.1 模型选择

我们的实验实现对重排序和嵌入任务均采用 BAAI 的 **BGE-m3** 模型 `[23][24]`。对于图构建与响应生成，我们使用 **gpt-4o-mini-2024-07-18** 进行图构建，并使用 **gpt-4o-mini-2024-07-18** 与 **gpt-4o-2024-11-20** 作为基于所给上下文生成响应的聊天智能体。

为了确保与 MemGPT 的 DMR 结果可直接比较，我们还使用 **gpt-4-turbo-2024-04-09** 进行了 DMR 评测。

实验 notebook 将通过我们的 GitHub 仓库公开，相关实验提示词包含在附录中。

### 4.2 Deep Memory Retrieval（DMR）

由 `[3]` 提出的 Deep Memory Retrieval 评测包含 **500 段多会话对话**，每段包含 5 个聊天会话，每个会话最多 12 条消息。每段对话包含一个用于记忆评测的问题/答案对。MemGPT 框架 `[3]` 目前以 **93.4%** 的准确率（使用 gpt-4-turbo）领先，相比通过递归摘要取得的 35.3% 基线有显著改进。

为建立可比较的基线，我们实现了两种常见的 LLM 记忆方法：**全对话上下文（full-conversation context）**与**会话摘要（session summaries）**。使用 gpt-4-turbo 时，全对话基线取得 **94.4%** 准确率，略高于 MemGPT 报告的结果，而会话摘要基线取得 **78.6%**。使用 gpt-4o-mini 时，两种方法的性能都有所提升：全对话 **98.0%**，会话摘要 **88.0%**。我们**无法使用 gpt-4o-mini 复现 MemGPT 的结果**，因为其发表的工作中方法细节不足。

随后我们评估 Zep 的性能：摄取这些对话，并使用其搜索函数检索**最相关的 10 个节点与边**。一个 LLM 裁判把智能体的回答与给定的金标准答案进行比较。Zep 使用 gpt-4-turbo 取得 **94.8%** 准确率，使用 gpt-4o-mini 取得 **98.2%**，相比 MemGPT 以及各自对应的全对话基线都有**微弱提升**。然而，这些结果必须放在语境中看待：每段对话只包含 60 条消息，可以轻松放进当前 LLM 的上下文窗口。

DMR 评测的局限不止于其规模偏小。我们的分析揭示了该基准设计上的显著弱点：评测完全依赖**单轮的事实检索问题**，无法评估复杂的记忆理解能力。许多问题措辞含糊，引用了诸如"favorite drink to relax with（用来放松的最爱饮品）"或"weird hobby（奇怪的爱好）"这类在对话中并未被如此明确刻画的概念。最关键的是，该数据集**不能很好地代表 LLM 智能体的真实企业用例**。使用现代 LLM 的简单全上下文方法就能取得高分，这进一步凸显了该基准在评估记忆系统方面的不足。

`[7]` 中的发现更进一步强调了这一不足：随着对话长度增加，LLM 在 LongMemEval 基准上的性能迅速下降。LongMemEval 数据集 `[7]` 通过提供更长、更连贯、更贴近企业场景的对话以及更多样化的评测问题，弥补了这些缺陷。

**表 1：Deep Memory Retrieval**

| 记忆方式 | 模型 | 分数 |
|---|---|---|
| Recursive Summarization†（递归摘要） | gpt-4-turbo | 35.3% |
| Conversation Summaries（会话摘要） | gpt-4-turbo | 78.6% |
| MemGPT† | gpt-4-turbo | 93.4% |
| Full-conversation（全对话上下文） | gpt-4-turbo | 94.4% |

### 4.3 LongMemEval（LME）

我们使用 **LongMemEvalₛ** 数据集评测 Zep，该数据集提供的对话与问题代表了 LLM 智能体在真实商业应用中的情形。LongMemEvalₛ 数据集对现有的 LLM 与商业记忆解决方案都构成了重大挑战 `[7]`，其对话长度平均约为 **115,000 token**。这一长度虽然可观，但仍在当前前沿模型的上下文窗口之内，使我们能够建立有意义的基线来评测 Zep 的性能。

该数据集包含**六种不同的问题类型**：single-session-user（单会话-用户）、single-session-assistant（单会话-助手）、single-session-preference（单会话-偏好）、multi-session（多会话）、knowledge-update（知识更新）和 temporal-reasoning（时序推理）。这些类别在数据集中并非均匀分布；详细分布信息请读者参阅 `[7]`。

我们所有的实验在 **2024 年 12 月至 2025 年 1 月**之间进行。测试使用一台消费级笔记本电脑，从马萨诸塞州波士顿的一处住宅位置连接到托管在 **AWS us-west-2** 的 Zep 服务。这一分布式架构在评测 Zep 性能时引入了额外的网络延迟，而这种延迟在基线评测中并不存在。

在答案评测方面，我们使用 **GPT-4o** 配合 `[7]` 提供的、针对具体问题类型的提示词，这些提示词已被证明与人类评估者高度相关。

#### 4.3.1 LongMemEval 与 MemGPT

为了在 Zep 与当前最先进的 MemGPT 系统 `[3]` 之间建立对比基准，我们尝试使用 LongMemEval 数据集评测 MemGPT。鉴于当前的 MemGPT 框架**不支持直接摄取已有的消息历史**，我们采用了一种变通做法：把对话消息添加到归档历史（archival history）中。然而，使用这一方法我们**未能获得成功的问答响应**。我们期待看到其他研究团队对这一基准的评测，因为对比性能数据将有利于 LLM 记忆系统的更广泛发展。

#### 4.3.2 LongMemEval 结果

与基线相比，Zep 在两种模型变体上都展现出**准确率与延迟上的显著改善**。使用 gpt-4o-mini 时，Zep 相比基线取得 **15.2%** 的准确率提升；使用 gpt-4o 时提升 **18.5%**。提示词规模的缩小还带来了相比基线实现的显著延迟成本削减。

## 5. 结论

我们提出了 Zep，一种基于图的 LLM 记忆方法，它同时纳入**语义记忆与情节记忆**，以及**实体摘要与社群摘要**。我们的评测表明，Zep 在已有的记忆基准上达到了最先进的性能，同时降低了 token 成本并以显著更低的延迟运行。

Graphiti 与 Zep 所取得的这些结果虽然令人印象深刻，但很可能只是基于图的记忆系统的初步进展。多条研究路径可以在这些框架之上继续推进，包括把其他 GraphRAG 方法整合进 Zep 范式，以及对我们工作的新颖扩展。

研究已经证明了**微调模型**在 GraphRAG 范式下做基于 LLM 的实体与边抽取的价值，能在提升准确率的同时降低成本与延迟 `[19][25]`。针对 Graphiti 的提示词做类似微调的模型，可能增强知识抽取能力，尤其是对复杂对话而言。此外，虽然当前关于 LLM 生成知识图谱的研究主要在**没有形式化本体（ontology）**的情况下进行 `[9][4][17][19][26]`，但**领域专属本体**具有显著潜力。图本体在前 LLM 时代的知识图谱工作中是基础性的，值得在 Graphiti 框架内进一步探索。

我们为寻找合适的记忆基准所做的检索显示可选方案有限，现有基准往往缺乏稳健性与复杂性，常常退化为简单的"大海捞针"式事实检索问题 `[3]`。该领域需要更多的记忆基准，特别是那些反映**商业应用**（如客户体验任务）的基准，以有效评估并区分各种记忆方法。值得注意的是，**目前没有基准能充分评估 Zep 把对话历史与结构化业务数据综合处理的能力**。虽然 Zep 聚焦于 LLM 记忆，但其传统 RAG 能力也应当对照 `[17]`、`[27]`、`[28]` 中的既有基准进行评估。

当前关于 LLM 记忆与 RAG 系统的文献，对生产系统在**成本与延迟**维度上的可扩展性讨论不足。我们为检索机制加入了延迟基准，以着手填补这一空白——这是效仿 LightRAG 作者优先关注这些指标的先例。

```text
{new_edge}
</NEW EDGE>
Task:
1. If the New Edges represents the same factual information as any edge
in Existing Edges, return 'is_duplicate: true' in the response.
Otherwise, return 'is_duplicate: false'
2. If is_duplicate is true, also return the uuid of the existing edge in
the response
Guidelines:
1. The facts do not need to be completely identical to be duplicates,
they just need to express the same information.
```

**中译要点**：给定下列上下文，判断新边是否表示了已有边列表中的某条边。任务：① 若新边与已有边中任一条表示同一事实信息，返回 `is_duplicate: true`，否则返回 `false`；② 若为重复，同时返回已有边的 uuid。准则：① 事实不一定要完全相同才算重复，只要表达相同的信息即可。（本条完整。）

#### 6.1.5 时间抽取（Temporal Extraction）

```text
<PREVIOUS MESSAGES>
{previous_messages}
</PREVIOUS MESSAGES>
<CURRENT MESSAGE>
{current_message}
</CURRENT MESSAGE>
<REFERENCE TIMESTAMP>
{reference_timestamp}
</REFERENCE TIMESTAMP>
<FACT>
{fact}
</FACT>
IMPORTANT: Only extract time information if it is part of the provided fact.
Otherwise ignore the time mentioned.
Make sure to do your best to determine the dates if only the relative time is
mentioned. (eg 10 years ago, 2 mins ago) based on the provided reference timestamp
If the relationship is not of spanning nature, but you are still able to
determine the dates, set the valid_at only.
Definitions:
- valid_at: The date and time when the relationship described by the
edge fact became true or was established.
- invalid_at: The date and time when the relationship described by the
edge fact stopped being true or ended.
Task:
Analyze the conversation and determine if there are dates that are part
of the edge fact. Only set dates if they explicitly relate to the
formation or alteration of the relationship itself.
Guidelines:
1. Use ISO 8601 format (YYYY-MM-DDTHH:MM:SS.SSSSSSZ) for datetimes.
2. Use the reference timestamp as the current time when determining
the valid_at and invalid_at dates.
3. If the fact is written in the present tense, use the Reference
Timestamp for the valid_at date
4. If no temporal information is found that establishes or changes the
relationship, leave the fields as null.
5. Do not infer dates from related events. Only use dates that are
directly stated to establish or change the relationship.
6. For relative time mentions directly related to the relationship, calculate the
actual datetime based on the reference timestamp.
7. If only a date is mentioned without a specific time, use 00:00:00 (midnight) for that date.
8. If only year is mentioned, use January 1st of that year at 00:00:00.
9. Always include the time zone offset (use Z for UTC if no specific
time zone is mentioned).
```

**中译要点**：重要——只有当时间信息属于所给事实的一部分时才抽取，否则忽略提到的时间。若只提到相对时间（如"10 年前"、"2 分钟前"），要基于给定的参考时间戳尽力确定日期。如果该关系不是"跨越性质"的，但你仍能确定日期，则只设置 `valid_at`。定义：`valid_at` = 该边事实所描述的关系变为成立/被建立的日期时间；`invalid_at` = 该关系不再成立/结束的日期时间。任务：分析对话，判断是否存在属于该边事实的日期；只有当日期明确地关系到关系本身的形成或变更时才设置。准则：① 使用 ISO 8601 格式（YYYY-MM-DDTHH:MM:SS.SSSSSSZ）；② 以参考时间戳作为"当前时间"来确定 valid_at/invalid_at；③ 若事实为现在时，用参考时间戳作为 valid_at；④ 若找不到确立或改变该关系的时间信息，字段留空（null）；⑤ 不要从相关事件推断日期，只用直接陈述的、确立或改变该关系的日期；⑥ 对与关系直接相关的相对时间表述，基于参考时间戳计算实际 datetime；⑦ 若只提到日期没有具体时间，用 00:00:00（午夜）；⑧ 若只提到年份，用该年 1 月 1 日 00:00:00；⑨ 始终包含时区偏移（未指定时区时用 Z 表示 UTC）。（本条完整。）

## 架构要点速览

| 维度 | 设计 |
|---|---|
| **记忆表示** | 时序感知动态知识图谱 𝒢 = (𝒩, ℰ, φ)，三层子图：情节子图 / 语义实体子图 / 社群子图 |
| **情节（Episode）** | 原始输入单元（message / text / JSON），**非损存储**；带参考时间戳 t_ref |
| **双时态模型** | T（事件时间线）+ T′（摄取事务时间线）；边上存 t_valid / t_invalid / t′_created / t′_expired 四个时间戳 |
| **实体抽取** | 当前消息 + 前 n=4 条消息 → 说话者必抽 → reflexion 式反思降幻觉 → 1024 维嵌入 + 全文搜索找候选 → LLM 消解 |
| **事实（边）抽取** | 同一事实可在多实体间重复抽取 = **超边**；边去重被限制在同一实体对内的边 |
| **边失效（核心创新）** | LLM 比对新边与语义相关旧边 → 识别时间重叠的矛盾 → 把旧边 t_invalid 设为新边 t_valid（**不物理删除**，且始终优先新信息） |
| **社群** | 标签传播（非 Leiden）→ 支持单步动态扩展 → 仍需周期性重建；社群名称嵌入以支持检索 |
| **检索三阶段** | f(α) = χ(ρ(φ(α)))：搜索 φ（余弦 + BM25 + BFS 三路）→ 重排序 ρ（RRF / MMR / 情节提及频次 / 节点距离 / cross-encoder）→ 构造器 χ（事实含有效期、实体名+摘要、社群摘要） |
| **写入策略** | 用**预定义 Cypher** 写入，不用 LLM 生成查询（保证模式一致、降幻觉） |
| **DMR 结果** | Zep 94.8%（gpt-4-turbo）/ 98.2%（gpt-4o-mini）vs MemGPT 93.4%、全上下文 94.4% |
| **LongMemEvalₛ 结果** | 准确率 +15.2%（gpt-4o-mini）/ +18.5%（gpt-4o）；延迟 31.3s → 3.20s（约 −90%）；上下文 115k → **1.6k token** |
| **最大短板** | single-session-assistant 类问题**下降**（gpt-4o −17.7%）；弱模型对时间数据理解不足 |
| **论文自陈局限** | 现有基准缺乏稳健性与复杂度；无基准能评估"对话 + 结构化业务数据"的综合能力；未能成功跑通 MemGPT 在 LongMemEval 上的对比 |
