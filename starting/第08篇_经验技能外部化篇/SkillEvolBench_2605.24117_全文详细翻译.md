## 摘要

大语言模型（LLM）agent 在解决真实任务时会累积丰富的情景轨迹，但这些经验能否被蒸馏成**可复用的程序化技能**仍不清楚。

我们提出 **SkillEvolBench**，一个用于评测「从经验复用走向技能形成」这一步的诊断性基准。它包含 **6 个真实 agent 环境、180 个任务**，组织成**共享潜在流程的角色条件化任务族**。Agent 从习得任务中学习，用**压缩后的轨迹与验证器反馈**更新一个**外部技能库**，随后面对**冻结的部署任务**，测试语境迁移、对抗性捷径与组合。

通过把**自生成**与**精选起点**的技能演化对照「无技能」与「原始轨迹」两个控制组，SkillEvolBench 把程序化抽象与以下三者分离开：基础能力、精选先验知识、以及对情景轨迹的直接复用。

在 **10 个模型配置与 3 个 agent harness** 上，我们发现**当前 agent 经常能局部适配，但很少形成稳健的可复用技能**。基于技能的条件可以改善习得或重放，个别模型有时在特定部署轴上有所增益，但**这些增益在冻结部署下不稳定**。**原始轨迹复用经常优于蒸馏出的技能**，说明当前的抽象过程丢弃了仍对未来任务有用的语境与程序性线索。容量与成本分析进一步显示，**写更多技能或更大的 Tier-3 资源库并不充分**：更多更新可以提高覆盖率，但也会引入**回合特有漂移与程序化杂乱**。

这些发现把 SkillEvolBench 定位为一个测试床，用来衡量**一次性的经验何时变成持久的程序化知识，而不是任务局部的记忆**。

## 1 引言

LLM agent 正越来越多地被部署为真实任务的实用接口。与静态问答系统不同，这些 agent 通过推理、调用工具、检查文件、执行代码与观察反馈，在多步轨迹上与外部环境交互 [1–4]。随着 agent 在更长的时间跨度上行动，**每一次任务尝试都留下一条情景轨迹，记录这次尝试是如何展开的**。已有工作表明这类经验可以被存储并在后续任务中复用 [5–8]。

**然而，复用一次情景与抽取一条流程并不等同。** 一条轨迹记录的是「发生过一次」的事，而且常常**把可迁移的决策与偶然细节、失败假设和错误混在一起**。未来任务极少精确重复同一个情景。它们需要一种更显式的**程序化形式**，说明**该再做什么、何时做、以及沿途该检查什么**。Agent 技能 [9, 10] 通过把可复用的 know-how 变成**外部制品**来弥合这一鸿沟——未来 agent 可以加载它们、在相关时调用它们、并在相关任务间遵循它们，而不必重放原始情景。

SkillsBench [11] 最近表明**精选技能能在多样领域上提升 agent 表现，而自生成技能平均收益甚微**。然而其自生成设置是**冷启动**的：agent 在尝试任务或观察验证器反馈**之前**就写出程序化指导。这就留下了**技能使用与技能形成之间的核心鸿沟**。如果精选技能表明程序化知识有用、经验复用方法表明轨迹含有解题证据，那么：**agent 能否把噪声重重的一次性经验蒸馏成紧凑技能，让未来 agent 能够加载、遵循并应用于原始情景之外，而不只是重放一条轨迹？**

**图 1  SkillEvolBench 探查情景化的 agent 经验能否被抽象为可复用的程序化技能。** 在习得期间，每一次合格尝试产出的执行日志制品被压缩成结构化的**轨迹摘要**，并与**验证器反馈**配对。一个**宿主侧 Skill Author 调用**——与解题 agent 循环相分离——利用这些证据与当前任务族的技能状态来**写入、精炼或跳过**一次技能库更新。所得的技能库在更难的部署任务之前被**冻结**，因此后续成功取决于先前的经验是否**已经**被转成可复用流程，而不是直接重放轨迹、持续适配或测试时修补。

1. **情景任务尝试**：agent 解题并产生轨迹。
2. **结构化验证器反馈**：失败测试、结果违规、过程违规、评分表诊断——完整轨迹在结构化验证器反馈下被审查。
3. **Skill Author**：写入新技能 / 精炼已有技能 / 什么都不做——由一个独立模型总结并从三种动作中选择一种。
4. **程序化技能库**：技能被存储，并使未来 agent 能在更难的任务上工作。

为研究这个问题，我们提出 **SkillEvolBench**——一个针对「情景经验」与「程序化复用」之间**缺失的一步**的诊断性基准。如图 1 所示，该基准把每一次学习尝试变成一个**抽象步骤**：一条情景轨迹与结构化验证器反馈被传给一个宿主侧 Skill Author 调用，后者决定是**写一个新技能、修订已有技能、还是保持技能库不变**。所得的技能库随后在更难的**相关**任务被评测之前被**冻结**，因此成功取决于**噪声重重的一次性经验是否已经被编码为可复用的流程**。

SkillEvolBench 覆盖从工程工作流到信息工作与职场运营的真实工作。它包含**六个环境，每个环境五个任务族**，每个任务族在相关问题之间共享一个**潜在的程序化模式**。在每个任务族内：

- **三个学习任务**：从一个规范情景走向**针对性变体**，暴露朴素流程的局限；
- **三个冻结评测任务**：测试在**语境迁移**、**对抗性捷径**与**多技能组合**下的迁移。

因此，性能反映的是 **agent 在见到更困难的相关任务之前，是否已从噪声情景中抽取出应该泛化的东西**。

我们在 **Self-Generated（自生成）** 与 **Curated-Start（精选起点）** 两种设置下评测这个问题。自生成设置测试 agent 能否**从自己的学习情景中归纳出技能**，而精选起点设置测试经验能否**改进人写的程序化先验**。我们把两者都与 **No-Skill** 和 **Raw-Trajectory** 控制组比较，并用最终冻结的技能库**重放**原始学习任务，以把**局部恢复**与**部署迁移**分开。

这一设计使技能演化的三个方面变得可度量：

1. SkillEvolBench 评测的是**技能形成**而非仅技能使用：每个任务族都要求 agent 在见到更困难的相关任务之前，把有验证器落地的情景转成一个**持久程序化制品**。
2. 它的**角色条件化任务弧**把习得、重放、迁移、语境迁移、对抗鲁棒性与组合分开，暴露出单一成功率会掩盖的失败模式。
3. 它的**控制组**把程序化抽象与基础 agent 能力、精选先验知识、以及对原始情景轨迹的直接复用区分开。

在 10 个模型配置与 3 个 agent harness 上，我们发现**当前 agent 表现出局部的程序化适配，但没有可靠的可复用技能形成**。基于技能的 agent 可以改善习得或重放，但这些增益**并不能一致地迁移到冻结部署任务上**。**Raw-Trajectory 控制组揭示了一个「有损抽象瓶颈」**：agent 常常**比从轨迹蒸馏出的技能更有效地使用情景轨迹本身**。进一步的诊断显示，瓶颈并不只是容量或成本：更大的资源库与更频繁的撰写在个别情况下有帮助，但它们也会引入**回合特有漂移、程序化杂乱与模型相关的失败**。

合起来，这些结果把 SkillEvolBench 定位为一个诊断测试床，用于研究**经验何时变成可复用的技能、何时仍只是回合特有的补丁、以及何时技能抽象会丢失未来任务所需的信息**。

## 2 相关工作

**从静态任务到真实 agent 工作。** Agent 基准已越来越多地从静态任务转向类似真实工作的交互式设置 [12, 13]。Mind2Web、MindWeb 与 WebArena 评测多步网页导航 [3, 14, 15]；SWE-bench 把软件工程评测建立在真实 GitHub issue 上 [4]；OSWorld、τ-bench 与 TheAgentCompany 把评测扩展到计算机使用、用户交互、工具策略与职场工作流 [16–18]。这些基准使 agent 评测更真实，但它们主要度量 **agent 能否完成任务**，而不是**它的经验是否变成后续相关任务可复用的流程**。

**复用 agent 经验。** 一支增长中的工作研究 agent 如何在不更新模型参数的情况下通过复用先前经验而改进。Reflexion 把言语反馈存入情景记忆 [5]；ExpeL 从累积经验中抽取教训 [6]；Synapse 把完整过去轨迹作为范例检索 [7]；Agent Workflow Memory 从网页 agent 执行中归纳可复用工作流 [8]。这些方法表明轨迹与反思含有有用的解题证据，但它们**主要复用情景轨迹或由此衍生的教训，而不是评测这类证据是否变成持久的程序化制品**。

**Agent 技能与技能演化。** Agent 技能通过把任务指导、脚本、参考与资源打包成可加载制品，使程序化知识显式化 [9, 10]。SkillsBench 表明精选技能可以提升性能，而冷启动自生成技能的平均增益有限 [11]。相关系统研究 LLM 生成的工具 [19, 20]、可执行代码技能库 [21]、以及技能发现、记忆技能、自演化或由轨迹衍生的技能库 [22–30]。SkillEvolBench 补充这些工作：它测试**有验证器落地的任务情景能否产出在冻结部署、语境迁移、对抗捷径与多技能组合下依然存续的外部技能制品**。

## 3 SkillEvolBench

### 3.1 概览

SkillEvolBench 评测 agent 能否把重复的任务经验转成可复用的程序化技能。它包含**六个真实 agent 环境中的 180 个任务**，每个环境**五个任务族**、每族**六个角色条件化任务**。每个任务族定义一条**技能演化弧**：任务共享一个底层流程，但**变化其失败模式、表面形式与部署条件**。这一设计把**任务特有修补**与**可被修订、调用和组合的技能**区分开。

### 3.2 环境与任务族

图 2 总结了这个分类法。六个环境覆盖常见的 agent 工作形态：

| 编号 | 环境 | 中文 |
|---|---|---|
| E1 | Code Debugging & Modification | 代码调试与修改 |
| E2 | Tool & API Orchestration | 工具与 API 编排 |
| E3 | Data Processing & Structured Query | 数据处理与结构化查询 |
| E4 | Document Parsing & Transformation | 文档解析与转换 |
| E5 | Research & Information Synthesis | 研究与信息综合 |
| E6 | Communication & Scheduling | 沟通与调度 |

**任务族指的是一种反复出现的程序化能力，而不是一个话题标签**，因此各任务族之间**足够相关以致经验有用，又足够多样以致能把程序化学习与话题记忆分开**。

**图 2  SkillEvolBench 把 agent 工作组织成受控的技能演化弧。** 基准跨六个真实环境、共 180 个任务，每个环境含五个反复出现的程序化任务族。每族遵循同样的**六角色推进**：**规范（canonical）、增强（enriched）、变体（variant）**任务暴露并压力测试目标流程，而**语境迁移（context-shift）、对抗（adversarial）、组合（composition）**任务评测演化出的技能**是否迁移、是否抵抗捷径、以及能否在真实工作流中与其他技能组合**。

### 3.3 任务构造

**任务选择。** 我们通过一个**来源驱动 + 人工精修**的过程构造 SkillEvolBench。**我们不复用任何已有基准实例。** 相反，我们用开源 agent 技能集合、面向技能的基准与实践者示例，作为任务主题与工作流母题的**证据来源** [10, 11, 31–33]。这些来源指导设计空间，但**不直接定义任务**。我们把观察到的工作流按**制品类型、所需工具、交互模式与解题流程**聚类，然后保留满足三项要求的任务族：

1. **真实世界相关性**；
2. **程序化技能适配性**；
3. **可验证的可演化性**。

具体地，每个任务族必须描述一条可复用流程，它**足够具体以致能写成技能、足够一般以致能迁移到一个固定装置之外、并且能通过确定性结果检查与过程级证据来评测**。

**角色条件化推进。** 对每个任务族，我们实例化六个角色。前三个支持技能习得：

- **canonical（规范）**：呈现基础流程；
- **enriched（增强）**：暴露一个缺失的子能力；
- **variant（变体）**：改变表面形式但保留同一流程。

后三个评测部署：

- **context-shift（语境迁移）**：把一个技能需求嵌入到更宽的请求中；
- **adversarial（对抗）**：引入能通过浅层检查的捷径解；
- **composition（组合）**：要求目标技能与其他技能交互。

这一推进测试**族级迁移、隐式调用、捷径抵抗与组合**。

**缺口暴露式精选技能。** 对每个任务族，我们提供一个**缺口暴露式精选技能**。它**既不是 oracle 解，也不是从任何任务实例复制而来**。我们先定义族级流程与**应当保持暴露的缺口**，再由一个技能创建器（skill-creator）依此规格起草初始技能 [34]，然后我们手工精修该草稿以控制其粒度。所得的技能应当**支持规范任务**，但**让增强、变体、对抗与组合情形保持未解决**；因此精选起点 agent 得到的是一个**有用但有界的初始化**，仍需要经验驱动的精炼。

**规格与审查。** 每个任务包含一条指令与固定装置、一个验证套件、以及一个评分表。验证套件包含：

- **公开测试**：检查基础契约；
- **隐藏测试**：检查边界情形与分布迁移；
- **过程验证器**：检查轨迹与制品中是否有脆弱策略，如硬编码常量、吞掉异常、跳过校验、或不完整修复。

在纳入之前，每个任务族与精选技能都被人工审查其**真实性、角色对齐、验证器覆盖度，以及精选技能是否「有用但不完整」**。完整规格见附录 A 与 B。

## 4 技能演化协议

### 4.1 协议概览

SkillEvolBench 中的每个环境都被评测为一个**独立的终身回合**。如图 3 所示，一个回合激活一个**全新的、环境局部的技能库**。Agent 先完成**习得任务**，其中记录下来的执行制品被压缩、并与验证器反馈配对，作为可能技能更新的证据（轨迹压缩的实现细节见附录 C.2）。所得的技能库随后针对部署被**冻结**。启用时，**重放**会用最终冻结的技能库重跑原始习得任务。切换到一个新环境会激活一个新技能库；先前环境的技能**只保留用于日志与审计，不会被挂载到下一个回合**。

**图 3  SkillEvolBench 评测协议。** 每个环境构成一个自包含的终身回合。

1. **初始化环境**：基于经验的自生成（从空技能库开始，再从经验归纳技能）或精选技能（从一个缺口暴露式精选技能开始）。
2. **在每个任务族内学习**：依次执行 canonical → enriched → variant 三个固定装置；每个固定装置产出轨迹与反馈，触发一次 Skill Author 动作；更新进入**环境特有的共享技能库**。
3. **冻结并评测**：评测期间不做任何技能库更新；在更难的任务上评测——**Context Shift / Adversarial / Composition**。
4. **重放**：在一个环境结束后，用最终冻结的演化库重放原始学习问题。度量**累积知识是否有助于它当初所依据的那些任务**。
5. **重置并切换环境**：把技能库重置为空，在下一个环境中独立重复该协议。

因此部署成功取决于事先的技能形成，而不是测试时修补；重放把**局部恢复**与**向更难角色的迁移**分开。重放之后，技能库在进入下一个环境之前被重置，以防止**跨环境泄漏**。

### 4.2 初始化与技能条件

我们比较三种初始化族级程序化知识的方式：

- **基于经验的自生成（experience-based self-generated）**：任务族从零技能开始；规范任务在没有族技能的情况下被尝试，**归纳只能在执行证据与验证器反馈可用之后发生**。
- **零样本生成（zero-shot generated）**：一个**仅基于元数据**的技能在执行之前生成并**保持不变**。
- **精选（curated）**：任务族从一个缺口暴露式精选技能开始，它覆盖基础流程，但**为习得任务留下暴露缺失子能力的空间**。精选种子在静态变体中固定，**只有在启用修订时才可被精炼**。

对任务族 $(e, f)$ 与条件 $c$，起始技能集为

$$S_c(e, f) = \begin{cases} \varnothing, & c = \text{exp-self} \\ \{\hat{s}^0_{e,f}\}, & c = \text{zero-shot} \\ \{s^{\text{gap}}_{e,f}\}, & c = \text{curated} \end{cases} \tag{1}$$

其中 $\hat{s}^0_{e,f}$ 表示零样本技能，$s^{\text{gap}}_{e,f}$ 表示 3.3 节定义的缺口暴露式精选种子；C.3 节给出零样本生成、基于经验的归纳与修订的撰写提示词。

### 4.3 习得：从情景证据到技能更新

令 $x^r_{e,f}$ 表示环境 $e$、任务族 $f$、角色 $r$ 中的任务。三个习得角色记为

$$R_{\text{acq}} = \{\text{can}, \text{enr}, \text{var}\} \tag{2}$$

即规范、增强与变体学习任务。

一个环境内的**所有习得任务都在部署开始之前完成**。活动技能库被限定在该环境内，因此**从较早任务族学到的技能对同一环境内较晚的任务族可见，但绝不会跨环境迁移**。族级起始技能 $S_c(e, f)$（存在时）在该族的规范任务被首次触及时引入。

每次习得尝试产出**一条压缩后的轨迹摘要** $\tilde{\tau}^r_{e,f}$，来自 harness 记录的制品，如指令、文件访问、工具调用、命令、编辑、生成的输出、测试与最终回复。验证器返回反馈 $v^r_{e,f}$，包含结果、过程检查、奖励与诊断。**我们不访问隐藏的模型状态或私有思维链。**

**技能撰写是族局部的。** 虽然解题 agent 可以读取环境级技能库，但 **Skill Author 只接收同任务族的技能与同任务族的习得历史**。在 can ≺ enr ≺ var 的次序下，角色 $r$ 之后的可用证据为

$$H^{\preceq r}_{e,f} = \left\{(\tilde{\tau}^{r'}_{e,f}, v^{r'}_{e,f})\right\}_{r' \in R_{\text{acq}},\ r' \preceq r} \tag{3}$$

Skill Author **只在合格的习得尝试之后**被调用，并发出一次结构化的技能库编辑：

$$L_{e,k+1} = U_c\left(L_{e,k},\ H^{\preceq r_k}_{e,f_k}\right) \tag{4}$$

更新规则 $U_c$ 依赖条件：

- 基于经验的自生成可在规范尝试之后归纳一个新技能，并在后续失败的习得尝试上修订它；
- **always-update** 变体在**每一次**合格的习得尝试之后调用撰写；
- 精选修订变体在同一触发策略下精炼精选种子，而**精选静态**保持其固定；
- 零样本技能**从不被修订**：

$$U_{\text{zero}}(L, H) = L \tag{5}$$

### 4.4 冻结部署与重放

习得之后，环境局部技能库被**冻结**。部署使用语境迁移、对抗与组合三个角色。部署期间 agent **可以读取与应用累积的技能，但不得创建、修订、退役或以其他方式修改技能库**。该阶段度量**先前的技能演化能否迁移到更难任务，而不允许在评测实例自身上做适配**。

当重放被启用时，我们用最终冻结的技能库重跑原始习得任务。**重放不更新技能库。** 它提供一个环境内的反事实：**同样的学习任务，一次在相关技能成熟之前被解决，一次在技能库演化之后被解决。**

### 4.5 评分

对每次任务尝试 $a$，验证器返回一个**结果分** $O_a$、一个**过程分** $P_a$、一个**总分** $G_a$ 与一个**二值成功指示** $B_a$。结果度量功能正确性（通过公开与隐藏测试），而过程度量 agent **是否遵循了预期流程**。对任意尝试集合 $I$，我们报告

$$\text{SR}(I) = \frac{1}{|I|}\sum_{a \in I} B_a \tag{6}$$

我们把 $\text{SR}(I)$ 实例化到协议定义的任务子集上：

| 指标 | 全称 | 含义 |
|---|---|---|
| **LSR** | Learning Success Rate | **习得**任务上的成功率：agent 走 canonical / enriched / variant 三角色，**期间仍允许技能更新**。 |
| **RSR** | Replay Success Rate | 环境技能库冻结后，在**原始习得任务**上的重放成功率。捕捉**局部恢复**而非迁移。 |
| **ESR** | Evaluation/Deployment Success Rate | **冻结部署**成功率，在留出的语境迁移、对抗与组合任务上，agent 可用但不可更新最终技能库。 |
| **CSSR** | Context-Shift SR | **语境迁移下的隐式技能调用**。 |
| **ARSR** | Adversarial SR | **对捷径解的鲁棒性**。 |
| **CompSR** | Composition SR | **多技能组合**。 |

即 $\text{ESR}$ 被分解为 $\text{CSSR} + \text{ARSR} + \text{CompSR}$。

#### 局部增益并不意味着可复用技能的形成

精选起点与自生成两种设置都显示出「技能改善了 LSR 或 RSR，却在部署指标上失败」的情形。例如：

- 在**自生成 Experience** 下，**Claude Opus 4.6** 相对 No-Skill 提升 LSR 5.5 pp、RSR 10.0 pp，但**降低了 ESR、CSSR 与 CompSR**。
- 同一条件下 **Claude Sonnet 4.6** 提升了 LSR、RSR、CSSR 与 CompSR，却在 **ARSR 上掉 10.0 pp**。
- 类似地，**GPT-5.2-Codex** 配 **Self-Generated + Always** 改善了多数指标，但在 ARSR 上仍比 No-Skill 低 10.0 pp。

这些例子表明，**重放恢复与局部改善可以反映有用的补丁，却不保证稳健的程序化复用**。

#### 部署指标暴露不同的失败模式

部署指标把**迁移、隐式调用、捷径抵抗与组合**分开。这种分离很重要，因为失败出现在不同轴上：

- **GPT-5.4** 配 **Curated-Start + Always** 改善了 ESR、ARSR 与 CompSR，却**降低了 CSSR**，提示当技能需求被嵌入到更宽语境中时出现**隐式调用失败**。
- **Gemini 3 Flash** 在同一条件下 CSSR 增益很强、CompSR 也有改善，但 **ARSR 急剧下降**，显示出**捷径脆弱性**。
- **GPT-5.4** 配 **Self-Generated Experience** 改善了 LSR、RSR 与 ARSR，却在 **CompSR 上失分**，表明**模块化较弱**。

因此，**单一成功率会掩盖技能究竟是通过过度专门化的修补、错失调用、依赖捷径，还是弱组合而失败**。

#### 原始轨迹揭示一个有损抽象瓶颈

图 4 提供了「从情景抽象到技能仍不可靠」的最清晰证据。**如果技能抽象保留了可复用流程，那么基于技能的条件应当匹配或超过 Raw-Trajectory。** 相反，**热力图在跨模型、跨变体、跨指标上以负值为主**。例如 **GPT-5.4** 配 **Self-Generated Experience** 在 LSR 与 RSR 上超过 Raw-Trajectory，却在 ESR、CSSR、ARSR 与 CompSR 上大幅落后。这表明**蒸馏出的技能可能在原始情景附近恢复了行为，却丢失了迁移、鲁棒性与组合所需的语境与程序性线索**。

#### 更多技能更新并非单调更好

**+ Always** 策略揭示出一种**覆盖—漂移权衡**。在自生成设置中，更频繁的更新可以改善部署侧覆盖：**GPT-5.2-Codex** 从 Experience 到 + Always 在 ESR 与 CSSR 上改善，**Gemini 2.5 Pro** 也在多个部署指标上获益。然而**总是更新可能降低局部增益**：**Gemini 3.1 Pro** 从 Experience 下强 LSR 与 RSR 改善回落到 + Always 下小得多的增益。在精选起点设置中，**+ Always 也不支配 + Revision**。

因此，**情景经验并不会仅仅因为它被更频繁地写入技能库就变成可复用技能**。Agent 需要这样的更新策略：**保持一般性、在回合特有细节固化之前过滤它们、并保留未来部署在语境迁移、对抗捷径与组合下所需的程序性线索**。

### 5.4 容量诊断：更多技能容量有帮助吗？

Raw-Trajectory 对比提示，紧凑的技能抽象可能丢弃有用的程序化证据。因此我们追问：agent 能否从执行轨迹中抽取足够多的可复用信息，**把技能库丰富到单个 `SKILL.md` 之外**？这些轨迹包含具体证据，包括被反复重新推导的命令、agent 希望自己早就有的校验脚本、运行时发现的 schema 细节、查找表、示例与模板。一个有能力的 Skill Author 应当能把这类证据转成 `scripts/`、`references/` 与 `assets/` 下的**持久资源**。所以问题不仅是「更大的技能库是否更好」，而是**额外的技能库容量是否有助于以未来 agent 能加载与应用的形式保留可复用的程序化结构**。

我们用 **Tier-3 强制**作为这个问题的诊断。在 **Always+Tier3** 消融中，**每一次**合格的修订**必须**为某个已有技能的 `scripts/`、`references/` 或 `assets/` 目录加入至少一个新或更新过的资源。非 Tier-3 的 Always 条件已经允许 Skill Author 在资源确实有帮助时添加它们，而 Tier-3 设置**把资源打包变成强制**。这在**普通自由形式的技能编辑**与**激进的资源打包**之间给出一个受控对比，同时保持轨迹证据、验证器反馈、已有技能状态与 Skill Author 调用接口在各条件间不变。

**如果容量是主要瓶颈**，那么 Always+Tier3 应当产出更丰富的技能库，同时保持或改善冻结部署成功。**如果真正的问题是选择性抽象而非存储**，那么技能库可能变大，而 ESR 在更难的部署角色上**持平或下降**。

**图 5 技能库规模与冻结评测成功。** 每个面板对应一个模型。横轴是最终技能库规模（`SKILL.md`、`references/`、`scripts/` 与 `assets/` 文件数），纵轴是 ESR。空心标记表示普通的 Always 修订，实心标记表示 Always+Tier3。连线把每个记忆条件连接到同一模型的 No-Skill 运行。

**图 5 把容量扩张与功能改善分开。** 强制 Tier-3 撰写**确实**让 agent 写出更丰富的技能库：Always+Tier3 变体通常会在 `scripts/`、`references/` 与 `assets/` 下添加更多文件。这表明 **agent 能够识别出看似可复用的、来自轨迹的材料**。**然而更大的技能库并不能可靠地改善冻结部署。** 图 5 中许多点**向右移动却没有向上移动**：持久化文件数增加，但 ESR 持平或下降。完整的分模型、分指标 Tier-3 消融结果见附录 D；它们在指标层面显示同样的模式——**额外资源有时改善习得或重放指标，但并不一致地改善冻结部署、语境迁移调用、对抗鲁棒性或多技能组合**。

**正向案例**表明，当额外资源捕捉到**解题 agent 确实能够复用的稳定流程**时，它们是有帮助的：**Claude Opus 4.6** 在 SelfGen-Always+Tier3 下 ESR 从 37.8% 提升到 **40.0%**，**Gemini 3.1 Pro** 在 Curated-Always+Tier3 下从 35.6% 提升到 **40.0%**。这些结果表明**有些程序化细节并未被完整保留在紧凑的 `SKILL.md` 正文中**。在这种情况下，Tier-3 文件可以发挥它们预期的作用——保留可复用的**校验例程、参考材料、模板或可执行辅助程序**，供未来 agent 按需加载。

**失败案例**则显示容量扩张在哪里崩塌：**GPT-5.4** 在 Curated-Always 下达到其最高 ESR，而更大的 Curated-Always+Tier3 与 SelfGen-Always+Tier3 技能库**降低了 ESR**。**Gemini 3 Flash** 是最清晰的过载案例：其 SelfGen-Always+Tier3 技能库属于最大的那一类，而 **ESR 从 No-Skill 的 35.6% 降到 27.8%**。**Claude Sonnet 4.5** 同样在 SelfGen-Always+Tier3 下从 35.6% 降到 30.0%。

这些下降表明，**强制的资源打包会保留那些「局部看似有用、却无法迁移到原始习得语境之外」的细节**。新增资源可能编码了**回合特有假设、过度专门的验证器、过时语境、或触发条件薄弱的文件**，从而在冻结评测期间**增加检索负担并分散 agent 注意力**。

总体而言，容量问题的答案**只是部分肯定的**。Agent 可以写出更多文件、把更多材料打包为持久技能资源，但它们**还不能可靠地保留正确的信息**。限制因素是**选择性丰富化（selective enrichment）**：**判断哪些细节足够稳定以致值得持久化、如何把它们组织成程序化资源、以及未来 agent 何时应当加载它们**。因此 Tier-3 从另一个角度暴露了同一个抽象瓶颈：**更多容量只有在受控时才有帮助；否则更丰富的技能库会变成程序化杂乱，而不是更可靠的技能**。

### 5.5 环境层面的成功模式

图 6 显示**环境结构是另一个大的变异来源**。在各基线之间：

- **LSR** 上，最容易与最难环境的差距是 **67.3 个百分点**；
- **ESR** 上，该差距是 **42.1 个百分点**。

相比之下，跨基线的对应范围**分别只有 1.9 与 5.4 个百分点**。这表明 **SkillEvolBench 并不只是在度量「加入记忆」的单一全局效应**，而是暴露出**情景经验被转成可复用程序化知识的难易程度存在领域特有的差异**。

**图 6  按基线划分的环境层面成功率。** 每个单元格报告一个基线与一个环境在模型—harness 运行上的平均成功率。列对应 E1 代码调试与修改、E2 工具与 API 编排、E3 数据处理与结构化查询、E4 文档解析与转换、E5 研究与信息综合、E6 沟通与调度。LSR 与 RSR 度量习得与重放成功，ESR 度量冻结部署成功。CSSR、ARSR 与 CompSR 把部署分解为语境迁移、对抗与组合三个角色。灰色单元格表示没有重放结果的变体。

关键读法：

- **E2 工具/API 的语境迁移成功率最高**，平均 CSSR 为 **84.7%**，说明一旦相关接口纪律可用，agent 常常能为**变化后的 API 语境**复用程序化模式。
- **E3 数据的对抗成功率最高**，平均 ARSR 为 **69.8%**，但其平均 **CompSR 只有 4.5%**。因此**对抗扰动鲁棒性与技能组合并不是可以互相替代的部署能力**。
- **E1 代码与 E4 文档**在**组合**上相对较强，而 **E6 沟通**在所有条件下都困难。特别是 **E6 对每个基线都得到 0.0% 的 CompSR**，凸显**沟通与调度是多约束程序化复用的困难设置**。

热力图也显示**基于技能的抽象并未一致地支配直接情景复用**。**Raw-Trajectory 是按平均 RSR、ESR、ARSR 与 CompSR 最强的基线**，平均值分别为 **48.2%、37.6%、44.7% 与 25.7%**。它在 **E4 文档解析与转换**与 **E5 研究与信息综合**上尤其有竞争力，因为**保留具体轨迹可以保住那些在抽象过程中可能丢失的、有用的任务特有细节**。同时，在结构化环境（如 E1 代码与 E4 文档）中的**重放改善**表明，**经验在习得之后是可以变成可复用的**。

合起来，这些模式提示：**技能演化在环境支持稳定程序化抽象时最可靠，而开放式信息与沟通任务仍然对缺失语境、欠约束条件与脆弱组合高度敏感**。

### 5.6 成本—成功分析

**图 7** 显示记忆机制在各模型间**并不形成统一的成本—成功前沿**。多数变体相对 No-Skill 提高了每个尝试任务的成本，但对应的 ESR 增益高度依赖模型与变体。这从配对线段的方向可见：**许多线段向右移动而几乎没有垂直移动，只有较小的一部分既向右又向上**。

**图 7  各模型相对 No-Skill 的成本—成功权衡。** 每个面板把 No-Skill 与一个记忆变体放在同样的十个模型上比较。横轴是每个尝试任务的成本（USD，对数刻度），纵轴是冻结评测成功率（ESR）。蓝色标记表示 No-Skill 运行，红色标记表示被比较的变体。灰色虚线线段连接同一模型的两个点。标记形状表示 agent harness。深色线标出每个两两比较中的 Pareto 前沿。

**静态精选技能并不充分。** **Curated-Static 平均而言劣于 No-Skill**：它改善 2 个模型、打平 1 个、**伤害 7 个**，平均 ESR 变化 **−2.44 个百分点**。这表明**固定的精选流程并不自动在部署迁移下有用**。当技能无法被修订时，它可能**过拟合到规范流程**，或为后续角色引入**误导性约束**。成本也平均**每个尝试任务增加 $0.077**，因此静态技能条件总体被 **No-Skill 与 Raw-Trajectory 支配**。
