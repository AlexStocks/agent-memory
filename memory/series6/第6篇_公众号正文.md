# Agent Memory 技术综述：有界召回篇

第 5 篇结尾，我写过一句判断：

**召回能力的天花板，是写入阶段决定的。**

这句话没错，但只说了一半。

写入决定池子里有什么。真正难的是池子已经很大、窗口只剩一点位置时：哪些证据还值得进上下文，哪些可以暂时退出，哪些一旦删掉就再也回不来。

这篇讲的就是「有界召回」。

它不是 reranker 调参，也不等于“上下文不够就做摘要”。它是一套带预算的证据决策：**留、整、删，以及为丢失的状态付账。**

> **赶时间**
>
> 先给结论：不要把“总是压缩”“按分数驱逐”“完成度没掉”当成记忆策略。预算紧时，整合可能比原样留存好；预算稍松，原始证据又可能更值钱。退出活跃池可以是可逆动作，物理删除不是。压缩后的完成度没掉，也可能只是把成本转成了后续反复检索。

## 00 · 先把“三篇主论文”这件事说清

原稿把 WMT、StructMem、Memento 称为“三篇主论文”。这个说法不严谨。

它们原本是为了搭叙事：WMT 管活跃集合，StructMem 管事件结构，Memento 管压缩上限。但“叙事上正好三条线”不等于“它们是有界记忆最该优先相信的三篇”。尤其 Memento 处理的是模型内部上下文和 KV cache，并不是外部 Agent Memory；把它与保留、驱逐、检索放成同一层，容易把问题讲歪。

这次我按三个标准重新取材：

| 选择标准 | 问的问题 |
|---|---|
| **问题直接性** | 是否直接研究有界记忆里的留、整、删或成本转移？ |
| **识别强度** | 是否控制了候选证据、预算、恢复干预或读取机制，而不只比较一个总分？ |
| **可审计性** | 结论能否落成工程日志、反事实检查或明确的验收指标？ |

据此，本文的三篇**核心证据**是：

1. **Retain or Consolidate?**：预算下，原文留存与整合何时翻转；
2. **What Eviction Destroys**：一次删除造成的损失，哪些已经不可恢复；
3. **What Does Context Compression Cost an Agent?**：压缩后，成本是否只是悄悄转成再获取。

这里的“核心”不是论文权威排名，更不是说另外几篇不重要。三篇都还是 arXiv 预印本：Retain or Consolidate 截至 2026-09-18 已更新到 v2，另外两篇仍是 v1。它们被放在最前面，只因为分别把三个最硬的决策钉得最紧。

StructMem 的 arXiv 页面标注为 ACL 2026 main conference 接收，发表状态比这三篇更强；它仍然会在后文出现，但作为“事件怎么组织”的实现路线，而不是替代上述三笔账。

## 01 · 有界召回不是排序问题，是三笔账

假设一个系统有候选记忆池，当前上下文预算是 `B`。它必须做的不是“挑 Top-K”，而是三类不同性质的决定：

```text
候选证据池
   |
   +-- 留原文，还是整合成更小表示？     信息保真账
   +-- 暂时不活跃，还是彻底驱逐？         可恢复性账
   +-- 压缩后少花的 token 到哪里去了？    运行时成本账
```

这三笔账不能混。

一条记忆没有排进本轮上下文，可能只是排序没命中；一条记忆被物理删除，是证据已经不在池子里；一段上下文被压短，模型也许还能完成任务，却可能在工具层多花很多轮去把丢掉的状态找回来。

把它们都压成一个“准确率”或“命中率”，系统会看起来很健康，实际已经在悄悄透支。

## 02 · 第一笔账：留原文，还是整合？

**Retain or Consolidate?** 问了一个比“摘要好不好”更有用的问题：预算从极紧变成稍松后，整合到底还是不是默认正确答案？

论文把“原文留存”“抽象”“合并”“改写”放到同一张桌子上比较。关键控制是：每种动作看到的都是同一批 gold 证据，变化的只有预算内如何表示它们。这样至少把“没找对证据”与“找对以后怎么装进预算”拆开了。

在 LongMemEval 的 32 token 极紧预算下，原样留存的得分是 **0.040**，抽象是 **0.400**，差 **0.360**。这不是微调收益，是真正装不下时，整合替你补回了覆盖面。

但预算到 256 token，原样留存 **0.480**、抽象 **0.453**；差异的置信区间跨过零，至少说明“压缩一定更好”已经站不住。论文在 LongMemEval 与 LoCoMo 上都观察到同方向的预算依赖：紧预算更需要整合，宽松预算更偏向保留原始细节。

这点很朴素：

- 装不下时，原文再完整也没有用，整合能让更多必要证据进场；
- 装得下时，摘要会丢掉时间、更正、否定和实体绑定，保留原文反而更稳。

所以不要把 `32` 和 `256` 当成可抄的阈值。它们依赖证据长度、模型、任务和候选质量。真正该抄的是决策方式：**先测自己的预算曲线，再决定何时整合；不要给所有查询套一个永远压缩的策略。**

论文还给了一个轻量 OAS 路由器，用生成前特征估计“此刻该留还是该整、该用哪种整合算子”。它值得借鉴，但不要把离线效用预测包装成在线真相：真实系统里的证据发现与表示决策是耦合的，论文的受控设计恰好把这层耦合隔开了。

## 03 · 第二笔账：退出活跃池，不等于可以销毁

如果说上一节在问“怎么装”，**What Eviction Destroys** 问的是“删掉以后，损失到底算谁的”。

很多系统只报一个结果：驱逐后准确率下降了多少。但这个数把三件事混在一起了：

1. 金标准证据已经被删，放回去答案才会变对，这是**不可逆损失**；
2. 金标准还在存储里，只是这次检索没取到，这是**可恢复损失**；
3. 证据在场，模型仍答错，这是**残余错误**。

这篇论文的恢复反事实做法很直接：对一个因驱逐而答错的问题，把被驱逐的金标准证据重新注入。如果答案由错变对，才把它记为删除真正造成的损失。

在 LongMemEval-S 的 80k token 预算下，FIFO、随机、冗余感知等策略中，不可逆损失占“不可逆 + 可恢复”错误的 **0.67-0.73**；预算压到 8k 时，这个比例到 **1.00**。这里不能理解为“任何 8k 系统一定全毁”，它只描述该基准、该读取机制和该实验设置下的分解结果。但它把一件工程常识变成了可检查的事实：**预算越紧，删除越像销毁证据，而不只是整理房间。**

这比“换一个更聪明的 eviction score”重要。论文还显示读取机制会改变结论：不控制检索配置，两个驱逐策略的预算-准确率曲线甚至没有可比性。只看最终命中率，可能是在拿“删错了”和“没取到”比较同一个指标。

工程里至少应该有四种状态：

| 状态 | 语义 | 是否可恢复 |
|---|---|---|
| `active` | 可直接进入当前检索/上下文 | 是 |
| `suppressed` | 暂时不参加默认竞争，但原文仍在 | 是 |
| `tombstoned` | 已退出在线路径，保留来源、版本和恢复索引 | 通常是 |
| `deleted` | 原文和可恢复载体都被清除 | 否 |

把 `suppressed` 直接实现为 `deleted`，是有界记忆里最昂贵的偷懒。业务或合规要求删除时当然应删；除此之外，先退出活跃集合、保留可审计的冷路径，往往更符合系统事实。

## 04 · 第三笔账：压缩省下的 token，可能变成了重查

**What Does Context Compression Cost an Agent?** 给这篇补上了最容易漏掉的一笔账。

通常我们会问：压缩以后，任务还做完了吗？这篇说，只报完成度不够。被压掉的状态可能让 agent 在后续不停调用工具重新确认；结果是完成度没显著变化，但交互预算已经被再获取吃掉了。

它把一次评估记成三元组：

```text
Y = (任务完成度, 检索/再获取调用, 执行调用)
```

在固定 24 轮视野的 IRBench 中，GPT-5.5 High 条件下，滑动压缩后的完成度从 **80% 到 85%**，配对检验 `p = 1.0`，看起来甚至略好；检索调用却从 **21.0** 升到 **63.9**，`p = 0.002`。论文在三个模型、两种体制的六组比较中都观察到检索调用上升，五组在 Holm 校正后仍显著。

它没有停在相关性。论文用 oracle 把被丢弃的、可外部查询的状态放回去，滑动条件的工具调用从 **72.9** 降到 **35.8**。这让“多出来的调用是在补丢失状态”不只是一个听起来合理的解释。

不过别把它改写成“压缩必然有害”。同一滑动策略在 ALFWorld 没有产生检索激增。压缩成本不是算子本身的固定属性，而取决于丢了什么状态、状态能否重新获得、模型会如何应对。

## 05 · 其他论文该放在哪里：不是陪衬，是边界和实现路线

核心证据只回答三笔账。它不意味着事件结构、活跃集合、安全和 KV 压缩不重要，而是它们回答的是不同问题。

| 问题 | 可参考的工作 | 这篇文章保留的判断 |
|---|---|---|
| 活跃集合怎么管理 | **WMT** | 状态驱动的竞争与抑制值得借鉴；但实验主要是 GAIA 式工具任务，不要直接当成跨会话用户画像方案。 |
| 检索单位是否应升到事件 | **StructMem** | 事件内绑定事实和关系是很好的实现路径；它是 ACL 2026 main 接收工作，但 LoCoMo 结果不能直接变成通用排序。 |
| 图结构什么时候有用 | **RippleMem**、**Selective Forgetting** | 查询时沿事件线索补证据，可能有效；静态图抽取在匹配候选预算下也可能输给扁平检索，不能因为“有图”就假设更强。 |
| 结构到底解决什么 | **MemSIF** | 结构应服务时间-结构错配和效用延迟，而不是把记忆做成更复杂的数据库。 |
| 压缩到模型内部会怎样 | **Memento** | 它是 KV cache / 上下文管理参照，不是外部记忆层方案；它提醒我们压缩文本和保留可用计算状态是两回事。 |

这里最值得留下的是反例意识。

Selective Forgetting 在匹配 5 个检索根的实验里，图记忆的 token F1 是 **0.417**，扁平向量基线是 **0.468**。它的遗忘模块能删掉约 9.8% 节点而质量没有显著变化，但“图表示天然赢检索”没有得到支持。

RippleMem 则提供了相反方向的证据：它的优势不在把所有东西预先压成图，而在查询命中后，沿事件线索再找缺失支撑。两个结果放在一起，比任何单篇的“图记忆很强”都更有用：**图不是能力，能否补齐当前问题缺的证据才是。**

安全也不能从有界策略里顺手推出。Utility Under Attack 用约 **1.2%** 的投毒语料测试，写时筛查拒绝了 **0 / 360** 条；来源加权能在一类语料上改善效用，却没有稳定工作点。结论不是“来源权重没用”，而是：**预算、排序和信任标签，都不能替代对被写入事实的安全验证。**

## 06 · 四条工程规则

前面的论文没有给出一套可直接复制的系统，但足够收敛出四条纪律。

### 6.1 按预算路由，不要固定压缩

先在自己的任务上画出“预算-效用”曲线。极紧预算允许整合优先；过渡区保留原文与整合表示并存；预算宽松时优先保留原始证据和版本链。

阈值要由本系统的证据长度、目标任务和模型测出来。论文里的 32、64、128、256 token 是实验刻度，不是生产配置。

### 6.2 生命周期显式化，抑制不等于删除

每条记忆至少记录来源、版本、时间、状态与状态变更原因。默认读取只面对 `active`，但恢复路径能查到 `suppressed` 和 `tombstoned`。

真正删除之前，抽样做恢复反事实：把退出的关键证据放回去，观察答案、工具调用或行动是否改变。这样才能知道是删错了、没召回，还是模型本来就不会用。

### 6.3 记录候选池，而不只记录最终命中

只留“最终给模型看的 Top-K”，无法解释为什么一条证据消失。每次决策至少记下：候选集合、入选与落选原因、预算、整合前后对应关系、状态迁移，以及最终是否被用到。

这份账既能定位召回问题，也能给删除审计留下证据。没有候选池日志，事后只能猜。

### 6.4 联合评估完成度、成本和可恢复性

一套最小看板可以是：

| 维度 | 最少要报什么 |
|---|---|
| 任务结果 | 完成度、答案正确率或行动成功率 |
| 运行时成本 | 输入 token、检索调用、执行调用、端到端延迟 |
| 证据状态 | 关键证据召回率、可回溯率、不可逆删除率 |
| 风险 | 冲突暴露率、投毒/不可信内容进入上下文的比例 |

一个策略只有“完成度没掉”，不能说明它更好。它可能只是把一次输入成本换成了三次工具调用，或者把不可逆错误藏在平均分后面。

## 07 · 写在最后

这篇改完，结论反而比原来简单。

有界召回没有一个万能策略。预算很紧，整合可以救命；预算稍松，原文可能更值钱。把一条记忆退出活跃集合，往往是正常管理；把它从可恢复路径里抹掉，则是另一种风险。压缩可以减少上下文，但省下来的预算不一定消失，可能只是挪到下一轮重查。

所以别只问“这次检索排第几”。先问四件事：

**这条证据为什么被整合？被抑制后还能回来吗？压缩后多花了多少再获取？出问题时能不能看见完整候选池？**

这才是有界记忆该有的工程底线。
